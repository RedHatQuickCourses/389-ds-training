#  Administer user passwords and reset policies.

= Administer User Passwords and Reset Policies

[abstract]
This section covers the essential administrative tasks of managing user passwords and implementing password reset policies within Red Hat Directory Server 13. You will learn how administrators can securely change a user's password and facilitate password resets, including forcing users to change their password on their next login.

== Introduction to Password Administration

Effective management of user passwords is a cornerstone of directory server administration and overall security. As an administrator, you will frequently perform tasks such as:

*   Setting initial passwords for newly created user accounts.
*   Modifying passwords for existing users upon request.
*   Resetting passwords when users forget their credentials or when their accounts are locked out due to security policies.

Red Hat Directory Server (RHDS) 13 provides robust command-line tools and mechanisms to perform these operations securely, often in conjunction with configured password policies.

== Administering User Passwords

Administrators possess the capability to directly set or change a user's password. This is typically achieved using command-line utilities such as `ldapmodify` for raw LDAP operations or `dsidm` for a more integrated and often simpler approach. When an administrator changes a password, it's crucial to consider the impact of existing password policies (e.g., complexity requirements, history checks), which may still apply depending on the policy configuration and the method used.

=== Changing a User's Password with `ldapmodify`

The `ldapmodify` utility allows for direct manipulation of directory entries, including the `userPassword` attribute. This method provides granular control and is suitable for scripting or complex operations.

.Syntax for changing a password using `ldapmodify`
[source,bash]
----
ldapmodify -h <RHDS_HOSTNAME> -p <PORT> -D "cn=Directory Manager" -w <DM_PASSWORD> -f <LDIF_FILE>
----

.Example LDIF File Content (`password_change.ldif`)
To change the password for a user `uid=testuser,ou=People,dc=example,dc=com` to `NewSecurePassword1!`:
[source,ldif]
----
dn: uid=testuser,ou=People,dc=example,dc=com
changetype: modify
replace: userPassword
userPassword: NewSecurePassword1!
----
*Ensure the new password meets any existing password complexity requirements.*

Apply the LDIF file:
[source,bash]
----
ldapmodify -h rhel-ds.example.com -p 389 -D "cn=Directory Manager" -w MyDirectoryManagerPassword -f password_change.ldif
----

=== Changing a User's Password with `dsidm`

The `dsidm` utility provides a user-friendly interface for managing RHDS instances and their data. It simplifies common administration tasks, including password changes for user accounts.

.Syntax for changing a user's password with `dsidm`
[source,bash]
----
dsidm -i <INSTANCE_NAME> user set --user-id <USERNAME> --set-password --new-password <NEW_PASSWORD>
----

.Example: Changing `testuser`'s password to `MyStrongPassword2!`
[source,bash]
----
dsidm -i rhel-ds user set --user-id testuser --set-password --new-password MyStrongPassword2!
----
This command will prompt you for the Directory Manager's password to authenticate the operation.

== Password Reset Policies and Procedures

Password resets are typically necessary in situations where users have forgotten their credentials, or their accounts have been locked due to excessive failed login attempts. As an administrator, you can perform a password reset, effectively assigning a new password to the user. A key security best practice is to force the user to change this administratively set password upon their next successful login.

=== Performing an Administrative Password Reset

An administrative password reset generally employs the same methods as an ordinary password change (`ldapmodify` or `dsidm`). The critical distinction lies in the context: a reset aims to restore access for a user who has lost it.

When performing a reset:

*   **Temporary Passwords:** It is common practice to set a temporary, strong password and securely communicate it to the user, instructing them to change it immediately after their first login.
*   **Forced Password Change:** Red Hat Directory Server password policies can be configured to force a user to change their password on the next successful bind if the password was set administratively. This significantly enhances security by ensuring only the user knows their long-term password.

=== Forcing Password Change on Next Login (`pwdReset`)

To compel a user to change their password upon their next login after an administrative reset, you can set the `pwdReset` operational attribute to `TRUE` for that specific user's entry. This attribute is an integral part of the `pwdPolicy` object class.

.Example LDIF for forcing password change after reset
To reset `uid=testuser`'s password to `TempPass4RHDS!` and force a change on next login:
[source,ldif]
----
dn: uid=testuser,ou=People,dc=example,dc=com
changetype: modify
replace: userPassword
userPassword: TempPass4RHDS!
-
add: pwdReset
pwdReset: TRUE
----
*Note the `-` separator, which is crucial for applying multiple modifications (replacing `userPassword` and adding `pwdReset`) to the same entry within a single LDIF file.*

Apply this LDIF using `ldapmodify`:
[source,bash]
----
ldapmodify -h rhel-ds.example.com -p 389 -D "cn=Directory Manager" -w MyDirectoryManagerPassword -f reset_with_force_change.ldif
----
After this operation, `testuser` will be prompted to change their password upon their next successful authentication, receiving an LDAP password policy error (e.g., `ldap_bind: Password policy error (8)`) until they do so. Once the user successfully changes their password (typically via the LDAP Password Modify extended operation), the `pwdReset` flag is automatically cleared by the server.

== Hands-on Lab: Administering User Passwords and Forcing Reset

In this lab, you will practice the complete workflow of administering a user's password: creating a user, changing their password as an administrator, and then performing a password reset with a forced change on their next login.

=== Prerequisites

*   A running Red Hat Directory Server 13 instance (e.g., named `rhel-ds`).
*   Directory Manager credentials for your RHDS instance.
*   Access to command-line tools: `ldapadd`, `ldapmodify`, `ldapsearch`, and `dsidm`.
*   Replace `rhel-ds.example.com` and `MyDirectoryManagerPassword` with your actual RHDS hostname/IP and Directory Manager password, respectively.

=== Lab Steps

.Create a Test User
Begin by creating a new user entry that will be used for testing password administration.
[source,bash]
----
ldapadd -h rhel-ds.example.com -p 389 -D "cn=Directory Manager" -w MyDirectoryManagerPassword -f - <<EOF
dn: uid=labuser,ou=People,dc=example,dc=com
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: labuser
cn: Lab User
sn: User
givenName: Lab
displayName: Lab User
mail: labuser@example.com
userPassword: InitialPa$$w0rd
EOF
----

.Verify Initial Password
Attempt to bind as `labuser` with the `InitialPa$$w0rd` to confirm the user was created successfully and can authenticate.
[source,bash]
----
ldapbind -h rhel-ds.example.com -p 389 -D "uid=labuser,ou=People,dc=example,dc=com" -w InitialPa$$w0rd
----
You should see output similar to `ldap_bind: success` indicating a successful bind.

.Change `labuser`'s Password as Administrator using `dsidm`
Now, acting as the Directory Manager, change `labuser`'s password to `Adm1nCh@ngedPa$$word!`.
[source,bash]
----
dsidm -i rhel-ds user set --user-id labuser --set-password --new-password Adm1nCh@ngedPa$$word!
----
You will be prompted to enter the Directory Manager password to authorize this operation.

.Verify New Password and Old Password Failure
First, attempt to bind with the *old* password (`InitialPa$$w0rd`). This should fail.
[source,bash]
----
ldapbind -h rhel-ds.example.com -p 389 -D "uid=labuser,ou=People,dc=example,dc=com" -w InitialPa$$w0rd
----
Expected output: `ldap_bind: Invalid credentials (49)` or similar.

Next, attempt to bind with the *new* password (`Adm1nCh@ngedPa$$word!`). This should succeed.
[source,bash]
----
ldapbind -h rhel-ds.example.com -p 389 -D "uid=labuser,ou=People,dc=example,dc=com" -w Adm1nCh@ngedPa$$word!
----
Expected output: `ldap_bind: success`.

.Perform an Administrative Password Reset with Forced Change
Imagine `labuser` has forgotten their password. As the administrator, you will reset it to `T3mp0raryP@ss!` and configure it so `labuser` *must* change it on their next successful login.

Create an LDIF file, for example, `reset_labuser_password.ldif`, with the following content:
[source,ldif]
----
dn: uid=labuser,ou=People,dc=example,dc=com
changetype: modify
replace: userPassword
userPassword: T3mp0raryP@ss!
-
add: pwdReset
pwdReset: TRUE
----

Apply these changes using `ldapmodify`:
[source,bash]
----
ldapmodify -h rhel-ds.example.com -p 389 -D "cn=Directory Manager" -w MyDirectoryManagerPassword -f reset_labuser_password.ldif
----

.Verify `pwdReset` Attribute and Forced Change Behavior
Attempt to bind as `labuser` using the *new temporary password* (`T3mp0raryP@ss!`).
[source,bash]
----
ldapbind -h rhel-ds.example.com -p 389 -D "uid=labuser,ou=People,dc=example,dc=com" -w T3mp0raryP@ss!
----
You should observe an `ldap_bind` error, typically `ldap_bind: Password policy error (8)` or `ldap_bind: Constraint violation (19)`, along with a message indicating that the password must be changed. This confirms the `pwdReset` flag is active and enforcing a password change.

To explicitly check the `pwdReset` attribute, perform an `ldapsearch` for the `labuser` entry:
[source,bash]
----
ldapsearch -h rhel-ds.example.com -p 389 -D "cn=Directory Manager" -w MyDirectoryManagerPassword -b "uid=labuser,ou=People,dc=example,dc=com" -s base "objectClass=*" pwdReset
----
The output should include:
[source]
----
...
pwdReset: TRUE
...
----
This confirms that the `pwdReset` attribute is set, requiring the user to change their password on the next successful authentication that performs a password modification operation.
