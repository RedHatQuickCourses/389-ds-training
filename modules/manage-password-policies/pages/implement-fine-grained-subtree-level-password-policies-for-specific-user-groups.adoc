#  Implement fine-grained (subtree-level) password policies for specific user groups.

= Manage Password Policies
:navtitle: Fine-Grained Password Policies

This section delves into the configuration and management of password policies within Red Hat Directory Server 13, with a specific focus on implementing fine-grained (subtree-level) policies for distinct user groups.

== Implementing Fine-Grained (Subtree-Level) Password Policies

While global password policies apply to all users within the directory, enterprise environments often require different security postures for different groups of users. For example, administrators might need more stringent password requirements than regular users, or users in a specific department might have unique compliance needs. Fine-grained password policies (FGPP) address this by allowing you to define and apply distinct password rules to specific subtrees or even individual user entries.

Fine-grained password policies in RHDS are based on the `ndsPasswordPolicy` object class, which provides a comprehensive set of attributes to control various aspects of password management, including complexity, aging, history, and lockout mechanisms. When an FGPP is applied to a subtree, it overrides the global password policy for all entries within that subtree that inherit the policy.

=== Understanding Password Policy Inheritance and Precedence

When multiple password policies could potentially apply to a user entry, RHDS follows a specific precedence rule:

1.  **Directly Applied Policy**: If a `pwdPolicySubentry` attribute points to a password policy directly on the user's entry, that policy takes precedence.
2.  **Subtree-Level Policy**: A policy specified on an Organizational Unit (OU) or other container entry via `pwdPolicySubentry` applies to all users within that subtree, unless overridden by a more specific policy. Policies applied closer to the user entry in the DIT (Directory Information Tree) hierarchy take precedence over policies applied higher up.
3.  **Global Policy**: If no specific subtree or user-level policy is applied, the global password policy configured for the directory instance (e.g., under `cn=Password Policy,cn=config`) is enforced.

This hierarchical approach provides flexibility, allowing administrators to define default policies globally while implementing stricter or more lenient policies for specific organizational units or groups as needed.

=== Key Attributes for Fine-Grained Password Policies

When creating an `ndsPasswordPolicy` entry, you'll configure various attributes to define its rules. Here are some of the most commonly used attributes:

*   `pwdMinLength`: Minimum number of characters allowed in a password.
*   `pwdMaxLength`: Maximum number of characters allowed in a password.
*   `pwdExpireWarning`: Number of days before password expiration to warn the user.
*   `pwdGraceLoginLimit`: Number of grace logins allowed after password expiration.
*   `pwdHistorySize`: Number of previous passwords that cannot be reused.
*   `pwdLockoutDuration`: How long an account remains locked out after exceeding failed attempts (in seconds).
*   `pwdFailureCountInterval`: The interval during which failed login attempts are counted (in seconds).
*   `pwdMaxFailure`: Maximum number of failed login attempts before the account is locked.
*   `pwdAllowUserChange`: Whether users are allowed to change their own passwords (`TRUE` or `FALSE`).
*   `pwdInHistory`: If `TRUE`, prevents reuse of previous passwords.
*   `pwdCheckQuality`: Controls password complexity requirements (e.g., requiring special characters, digits, mixed case). This is often an OID pointing to a specific password quality check plugin.
*   `pwdMinAge`: Minimum time (in seconds) that must pass before a user can change their password again.
*   `pwdMaxAge`: Maximum password lifetime (in seconds) before it expires.
*   `pwdPolicyEnabled`: If `TRUE`, the policy is active.

NOTE: Password-related attributes like `pwdMaxAge` and `pwdLockoutDuration` are typically defined in seconds.

=== Hands-on Lab: Configure and Test Fine-Grained Password Policies

In this lab, you will configure a fine-grained password policy for a specific Organizational Unit (OU) within your directory. This policy will override the global policy for users within that OU, demonstrating the power of subtree-level control.

==== Lab Objective

*   Create a new `ndsPasswordPolicy` entry with specific requirements.
*   Apply this policy to an existing Organizational Unit (OU).
*   Create a test user within the OU and verify the policy's enforcement.

==== Prerequisites

*   A running Red Hat Directory Server 13 instance.
*   `ldapadd`, `ldapmodify`, `ldapsearch` command-line utilities installed and configured.
*   Administrative access to the directory (e.g., `cn=Directory Manager`).
*   An existing base DN for your directory, for example, `dc=example,dc=com`.
*   An existing OU, or the ability to create one, for example, `ou=finance,dc=example,dc=com`.

==== Instructions

. **Step 1: Create a New Organizational Unit (OU) for Testing (if it doesn't exist)**
We will create an OU named `finance` to apply our fine-grained policy.

[source,bash]
----
cat > add_finance_ou.ldif << EOF
dn: ou=finance,dc=example,dc=com
objectClass: organizationalUnit
ou: finance
EOF

ldapadd -x -D "cn=Directory Manager" -W -f add_finance_ou.ldif
----
. **Step 2: Define the Fine-Grained Password Policy**
Create an LDIF file to define your new password policy. This policy will require a minimum password length of 10 characters, prevent reuse of the last 3 passwords, and lock out accounts after 3 failed attempts for 300 seconds (5 minutes).

[source,bash]
----
cat > add_finance_pwdpolicy.ldif << EOF
dn: cn=FinancePolicy,ou=policies,dc=example,dc=com
objectClass: top
objectClass: ndsPasswordPolicy
cn: FinancePolicy
pwdMinLength: 10
pwdHistorySize: 3
pwdMaxFailure: 3
pwdLockoutDuration: 300
pwdFailureCountInterval: 300
pwdMaxAge: 2592000
pwdExpireWarning: 604800
pwdPolicyEnabled: TRUE
EOF

# Ensure 'ou=policies' exists, or adjust the DN for the policy
# If 'ou=policies' does not exist, create it first:
# ldapadd -x -D "cn=Directory Manager" -W << EOL
# dn: ou=policies,dc=example,dc=com
# objectClass: organizationalUnit
# ou: policies
# EOL

ldapadd -x -D "cn=Directory Manager" -W -f add_finance_pwdpolicy.ldif
----
NOTE: It's good practice to organize your password policies under a dedicated OU, such as `ou=policies`. Adjust the `dn` accordingly if you prefer a different location.

. **Step 3: Verify the Policy Creation**
Use `ldapsearch` to ensure the policy entry was created successfully.

[source,bash]
----
ldapsearch -x -D "cn=Directory Manager" -W -b "cn=FinancePolicy,ou=policies,dc=example,dc=com"
----
You should see the attributes of your `FinancePolicy` listed.

. **Step 4: Apply the Policy to the `finance` OU**
Now, modify the `ou=finance` entry to point to your new password policy using the `pwdPolicySubentry` attribute.

[source,bash]
----
cat > modify_finance_ou.ldif << EOF
dn: ou=finance,dc=example,dc=com
changetype: modify
add: pwdPolicySubentry
pwdPolicySubentry: cn=FinancePolicy,ou=policies,dc=example,dc=com
EOF

ldapmodify -x -D "cn=Directory Manager" -W -f modify_finance_ou.ldif
----

. **Step 5: Create a Test User in the `finance` OU**
Create a new user, `user1`, within the `ou=finance` OU.

[source,bash]
----
cat > add_finance_user.ldif << EOF
dn: uid=user1,ou=finance,dc=example,dc=com
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: user1
cn: User One
sn: One
givenName: User
mail: user1@example.com
userPassword: password
EOF

ldapadd -x -D "cn=Directory Manager" -W -f add_finance_user.ldif
----
When prompted for `password`, enter a password that does *not* meet the `pwdMinLength: 10` requirement (e.g., `test`). You should receive an error indicating that the password does not meet the policy.

Now, try again with a password that meets the policy (e.g., `SecureP@ss1`).

[source,bash]
----
# Re-run the ldapadd command to add the user with a valid password
ldapadd -x -D "cn=Directory Manager" -W -f add_finance_user.ldif
----
Enter `SecureP@ss1` when prompted for the password. This time, the user should be added successfully.

. **Step 6: Test Password Policy Enforcement (Min Length and Lockout)**

*   **Test Minimum Length**:
    Attempt to change `user1`'s password to something shorter than 10 characters (e.g., `short`).

    [source,bash]
    ----
    ldappasswd -x -D "uid=user1,ou=finance,dc=example,dc=com" -W -s short
    ----
    You should get an error similar to `ldap_result: Constraint violation (19)` or `password fails quality policy`.

*   **Test Account Lockout**:
    Attempt to bind as `user1` with an incorrect password multiple times (more than 3 times, as per `pwdMaxFailure: 3`).

    [source,bash]
    ----
    # Attempt to bind with incorrect password (repeat 4 times)
    ldapwhoami -x -D "uid=user1,ou=finance,dc=example,dc=com" -W
    ----
    After a few attempts, you should receive an error indicating authentication failure, and further attempts will show the account is locked.

    To verify the lockout status, search for the user's entry and look for the `pwdAccountLockedTime` attribute.

    [source,bash]
    ----
    ldapsearch -x -D "cn=Directory Manager" -W -b "uid=user1,ou=finance,dc=example,dc=com" pwdAccountLockedTime
    ----
    If the account is locked, `pwdAccountLockedTime` will have a value. The account will unlock automatically after `pwdLockoutDuration` (300 seconds).

    To manually unlock the account, you can reset the `pwdAccountLockedTime` attribute.

    [source,bash]
    ----
    cat > unlock_user1.ldif << EOF
    dn: uid=user1,ou=finance,dc=example,dc=com
    changetype: modify
    delete: pwdAccountLockedTime
    EOF

    ldapmodify -x -D "cn=Directory Manager" -W -f unlock_user1.ldif
    ----

. **Step 7: Clean Up (Optional)**
Remove the test user, the `finance` OU, and the password policy.

[source,bash]
----
ldapdelete -x -D "cn=Directory Manager" -W "uid=user1,ou=finance,dc=example,dc=com"
# Remove the pwdPolicySubentry attribute from the OU before deleting the OU
cat > cleanup_ou_policy.ldif << EOF
dn: ou=finance,dc=example,dc=com
changetype: modify
delete: pwdPolicySubentry
EOF
ldapmodify -x -D "cn=Directory Manager" -W -f cleanup_ou_policy.ldif

ldapdelete -x -D "cn=Directory Manager" -W "ou=finance,dc=example,dc=com"
ldapdelete -x -D "cn=Directory Manager" -W "cn=FinancePolicy,ou=policies,dc=example,dc=com"
# Optionally, delete the ou=policies container if it's empty and no longer needed
ldapdelete -x -D "cn=Directory Manager" -W "ou=policies,dc=example,dc=com"
----

This lab demonstrates how to effectively implement and test fine-grained password policies, providing granular control over user authentication security based on organizational structure.

=== Troubleshooting Fine-Grained Password Policies

*   **Policy Not Applying**:
    *   **Check DNs**: Ensure the `pwdPolicySubentry` attribute on the target OU or user entry correctly points to the `dn` of the `ndsPasswordPolicy` entry.
    *   **Hierarchy**: Verify that the user entry is actually within the subtree where the policy is applied.
    *   **Typo in Attributes**: Double-check the attribute names and values in your LDIF file for typos.
    *   **Policy Enabled**: Ensure `pwdPolicyEnabled: TRUE` is set on the policy entry.
    *   **Schema Consistency**: Confirm that the `ndsPasswordPolicy` object class is correctly defined in your directory schema.
    *   **Caching**: In some cases, directory server caching might delay policy enforcement. A server restart can sometimes help, but usually, policy changes are immediate.

*   **Unexpected Policy Behavior**:
    *   **Precedence Issues**: If multiple policies could apply, understand the precedence rules. Use `ldapsearch` to check the `pwdPolicySubentry` attribute on the user and all parent OUs to trace which policy is being applied.
    *   **Global Policy Interference**: If a global policy is very permissive or conflicting, it might appear to override your fine-grained policy if the FGPP is misconfigured or not correctly linked.

*   **Password Quality Checks**:
    *   If you're using `pwdCheckQuality`, ensure that the associated plugin is installed and correctly configured in the `cn=plugins,cn=config` section of the directory server. The OID value for `pwdCheckQuality` must correspond to an active plugin.

*   **Account Lockout Issues**:
    *   Monitor the `pwdAccountLockedTime` attribute on user entries.
    *   Check `pwdLockoutDuration` and `pwdFailureCountInterval` for expected behavior. Ensure durations are set in seconds.

*   **Logging**:
    *   Enable detailed password policy logging in RHDS configuration. This can provide valuable insights into why a password attempt was rejected or why an account was locked. Look for specific error messages in the `errors` log file (e.g., `/var/log/dirsrv/slapd-your_instance/errors`).
    *   Set the `cn=config,cn=pwdpolicy,cn=plugins,cn=config` logging level to `512` for detailed debugging.

By carefully following these steps and understanding the underlying mechanisms, you can effectively implement and manage fine-grained password policies, significantly enhancing the security posture of your Red Hat Directory Server 13 environment.
