#  Hands-on Lab: Configure and test global and fine-grained password policies.

= Manage Password Policies
:nav_title: Hands-on Lab: Configure and test global and fine-grained password policies
:page-aliases: training/password_policies/lab_password_policies.adoc
:page-tag: lab, password, policies, global, fine-grained, rhds, ldap

This hands-on lab guides you through the process of configuring and testing both global and fine-grained password policies within Red Hat Directory Server 13. By the end of this lab, you will be able to enforce password complexity, aging, and account lockout rules across your directory and for specific user groups.

[role="page-introduction"]
Red Hat Directory Server provides robust password policy management capabilities. A *global password policy* applies to all users in the directory, while *fine-grained password policies* allow you to define distinct rules for specific subtrees or user groups, providing flexibility for diverse organizational requirements.

== Objectives

Upon completion of this lab, you will be able to:

*   Configure a global password policy including complexity, aging, and lockout settings.
*   Verify the global password policy's enforcement.
*   Create and apply a fine-grained password policy to a specific organizational unit (OU).
*   Test the enforcement of a fine-grained password policy.

== Prerequisites

*   A running Red Hat Directory Server 13 instance on RHEL 9.
*   Administrative access to the RHDS instance (e.g., `cn=Directory Manager`).
*   Basic familiarity with `dsconf`, `ldapadd`, `ldapmodify`, and `ldapsearch` commands.
*   An existing base DN, for example, `dc=example,dc=com`.

== Lab Environment Setup

Ensure your RHDS instance is running and you can authenticate as `Directory Manager`.

.Log in as `root` (or a user with `sudo` privileges) to your RHDS server.
.Start the RHDS instance if it's not already running:
+
[source,bash]
----
sudo dsctl _instance_name_ start
----
+
Replace `_instance_name_` with the actual name of your RHDS instance (e.g., `ds1`).

=== Create a Test User

Before configuring policies, let's create a test user that we can use to observe the policy effects. We'll add this user to an existing suffix, `dc=example,dc=com`.

.Create an LDIF file named `test_user.ldif` with the following content:
+
[source,ldif]
----
dn: uid=testuser1,ou=users,dc=example,dc=com
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: testuser1
cn: Test User One
sn: UserOne
givenName: Test
displayName: Test User One
mail: testuser1@example.com
userPassword: password123
----
+
*Note*: We'll intentionally set a simple password here to test policy enforcement later.

.Add the user to the directory:
+
[source,bash]
----
ldapadd -x -D "cn=Directory Manager" -W -f test_user.ldif -H ldapi:///
----
+
You will be prompted for the Directory Manager password.

.Verify the user creation:
+
[source,bash]
----
ldapsearch -x -D "cn=Directory Manager" -W -b "ou=users,dc=example,dc=com" "uid=testuser1"
----

== Configure Global Password Policies

Red Hat Directory Server provides a default global password policy, but you can customize it to meet specific security requirements. These settings are typically found under `cn=config,cn=ldif directory,cn=plugins,cn=config` or can be managed with `dsconf`.

We will configure the following global password policy rules:

*   Minimum password length: 8 characters
*   Password complexity: require at least one uppercase, one lowercase, one digit, one special character.
*   Password expiration: 30 days
*   Password history: Remember last 5 passwords
*   Account lockout: Lockout after 3 failed attempts within 300 seconds (5 minutes), for 300 seconds.

.Set the global password policy attributes using `dsconf`. Replace `_instance_name_` with your instance name.
+
[source,bash]
----
sudo dsconf -D "cn=Directory Manager" ldapi:/// _instance_name_ password policy set \
--min-length 8 \
--check-quality ON \
--max-age 2592000 \
--expire-warning 604800 \
--max-history 5 \
--max-failures 3 \
--failure-count-interval 300 \
--lockout-duration 300
----
+
*   `--min-length 8`: Sets `pwdMinLength` to 8.
*   `--check-quality ON`: Enables `pwdCheckQuality`, which uses the server's internal password quality check module (often including character class requirements).
*   `--max-age 2592000`: Sets `pwdMaxAge` to 30 days (2592000 seconds).
*   `--expire-warning 604800`: Sets `pwdExpireWarning` to 7 days (604800 seconds).
*   `--max-history 5`: Sets `pwdHistory` to 5.
*   `--max-failures 3`: Sets `pwdMaxFailure` to 3.
*   `--failure-count-interval 300`: Sets `pwdFailureCountInterval` to 300 seconds.
*   `--lockout-duration 300`: Sets `pwdLockoutDuration` to 300 seconds.

.Verify the global password policy settings.
+
[source,bash]
----
sudo dsconf -D "cn=Directory Manager" ldapi:/// _instance_name_ password policy get
----
+
You should see the configured values for `pwdMinLength`, `pwdCheckQuality`, `pwdMaxAge`, etc.

=== Test Global Password Policy Enforcement

Now, let's test if the global policy is being enforced.

. *Test Minimum Length and Complexity*: Try to change `testuser1`'s password to something that violates the new policy.
+
[source,bash]
----
ldappasswd -x -D "cn=Directory Manager" -W -s "simple" -w "password123" "uid=testuser1,ou=users,dc=example,dc=com"
----
+
You should receive an error message similar to: `LDAP Result: 53 (Unwilling to perform) - The password fails to satisfy the policy.`

. *Set a Compliant Password*: Change `testuser1`'s password to a compliant one (e.g., `SecureP@ssw0rd!`).
+
[source,bash]
----
ldappasswd -x -D "cn=Directory Manager" -W -s "SecureP@ssw0rd!" -w "password123" "uid=testuser1,ou=users,dc=example,dc=com"
----
+
This command should succeed.

. *Test Password History*: Try to change `testuser1`'s password back to `password123` (the original one from setup).
+
[source,bash]
----
ldappasswd -x -D "cn=Directory Manager" -W -s "password123" -w "SecureP@ssw0rd!" "uid=testuser1,ou=users,dc=example,dc=com"
----
+
You should receive an error indicating a history violation: `LDAP Result: 53 (Unwilling to perform) - The password is in the history of previously used passwords.`

. *Test Account Lockout*:
    .. Attempt to bind as `testuser1` with incorrect passwords multiple times (more than `pwdMaxFailure` which is 3).
    +
    [source,bash]
    ----
    ldapwhoami -x -D "uid=testuser1,ou=users,dc=example,dc=com" -w "wrongpass1"
    ldapwhoami -x -D "uid=testuser1,ou=users,dc=example,dc=com" -w "wrongpass2"
    ldapwhoami -x -D "uid=testuser1,ou=users,dc=example,dc=com" -w "wrongpass3"
    ldapwhoami -x -D "uid=testuser1,ou=users,dc=example,dc=com" -w "wrongpass4" # This should trigger lockout
    ----
    +
    After the third failed attempt, subsequent attempts will result in an error like: `LDAP Result: 48 (Confidentiality required) - Account locked.` or `LDAP Result: 53 (Unwilling to perform) - Account locked due to too many authentication failures.`
    .. Wait for the `pwdLockoutDuration` (300 seconds or 5 minutes) or manually unlock the account.
    .. To manually unlock, find the `pwdAccountLockedTime` attribute and remove it.
    +
    [source,bash]
    ----
    ldapsearch -x -D "cn=Directory Manager" -W -b "uid=testuser1,ou=users,dc=example,dc=com" "uid=testuser1" pwdAccountLockedTime
    ----
    +
    If `pwdAccountLockedTime` is present, delete it:
    +
    [source,ldif]
    ----
    dn: uid=testuser1,ou=users,dc=example,dc=com
    changetype: modify
    delete: pwdAccountLockedTime
    ----
    +
    Save this as `unlock_user.ldif` and apply it:
    +
    [source,bash]
    ----
    ldapmodify -x -D "cn=Directory Manager" -W -f unlock_user.ldif -H ldapi:///
    ----
    .. After the account is unlocked (either manually or after the duration), you should be able to bind with the correct password:
    +
    [source,bash]
    ----
    ldapwhoami -x -D "uid=testuser1,ou=users,dc=example,dc=com" -w "SecureP@ssw0rd!"
    ----

== Configure Fine-Grained Password Policies

Fine-grained password policies allow you to apply different password rules to specific subtrees or groups of users, overriding the global policy. This is achieved by creating a `pwdPolicy` entry and linking it to an organizational unit (OU) or a user entry using the `pwdPolicySubentry` attribute.

Let's create an OU for "Special Users" and apply a more stringent password policy to it.

.Create a new organizational unit (`ou=specialusers,dc=example,dc=com`) and a user within it.
+
[source,ldif]
----
dn: ou=specialusers,dc=example,dc=com
objectClass: organizationalUnit
ou: specialusers

dn: uid=specialuser1,ou=specialusers,dc=example,dc=com
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: specialuser1
cn: Special User One
sn: UserOne
givenName: Special
displayName: Special User One
mail: specialuser1@example.com
userPassword: password123
----
+
Save this as `special_users.ldif` and add it:
+
[source,bash]
----
ldapadd -x -D "cn=Directory Manager" -W -f special_users.ldif -H ldapi:///
----

.Define a fine-grained password policy. We'll make it *more stringent* than the global policy:
    *   Minimum length: 10 characters
    *   Max age: 60 days
    *   Account lockout: Lockout after 2 failed attempts within 120 seconds.

.Create an LDIF file named `fg_policy.ldif` with the following content. We'll define this policy under the `cn=Password Policies,cn=config` container.
+
[source,ldif]
----
dn: cn=SpecialUsersPolicy,cn=Password Policies,cn=config
objectClass: top
objectClass: pwdPolicy
cn: SpecialUsersPolicy
pwdMinLength: 10
pwdMaxAge: 5184000
pwdMaxFailure: 2
pwdFailureCountInterval: 120
pwdLockoutDuration: 120
pwdCheckQuality: ON
pwdGraceAuthNLimit: 0
pwdAllowUserChange: TRUE
pwdInHistory: 5
----
+
*Note*: For `pwdPolicy` entries, `pwdInHistory` is used instead of `pwdHistory` when defining the policy object itself. `pwdHistory` is an operational attribute on the user entry.

.Add this fine-grained password policy to the directory:
+
[source,bash]
----
ldapadd -x -D "cn=Directory Manager" -W -f fg_policy.ldif -H ldapi:///
----

.Apply the fine-grained policy to the `ou=specialusers,dc=example,dc=com` subtree by setting the `pwdPolicySubentry` attribute on the OU.
+
[source,ldif]
----
dn: ou=specialusers,dc=example,dc=com
changetype: modify
add: pwdPolicySubentry
pwdPolicySubentry: cn=SpecialUsersPolicy,cn=Password Policies,cn=config
----
+
Save this as `apply_fg_policy.ldif` and apply it:
+
[source,bash]
----
ldapmodify -x -D "cn=Directory Manager" -W -f apply_fg_policy.ldif -H ldapi:///
----

.Verify the `pwdPolicySubentry` on the `ou=specialusers` entry.
+
[source,bash]
----
ldapsearch -x -D "cn=Directory Manager" -W -b "ou=specialusers,dc=example,dc=com" "objectClass=*" pwdPolicySubentry
----
+
You should see the `pwdPolicySubentry` pointing to `cn=SpecialUsersPolicy,cn=Password Policies,cn=config`.

=== Test Fine-Grained Password Policy Enforcement

Now, let's test if the `SpecialUsersPolicy` is being enforced for `uid=specialuser1`.

. *Test Minimum Length*: Try to set a password of 8 characters (which would be compliant with the *global* policy but not the *fine-grained* one) for `specialuser1`.
+
[source,bash]
----
ldappasswd -x -D "cn=Directory Manager" -W -s "TestP@ss" -w "password123" "uid=specialuser1,ou=specialusers,dc=example,dc=com"
----
+
You should receive an error indicating a policy violation (minimum length 10): `LDAP Result: 53 (Unwilling to perform) - The password fails to satisfy the policy.` This confirms the fine-grained policy is active.

. *Set a Compliant Password for Special User*: Change `specialuser1`'s password to a compliant one (e.g., `LongSecureP@ssw0rd!`).
+
[source,bash]
----
ldappasswd -x -D "cn=Directory Manager" -W -s "LongSecureP@ssw0rd!" -w "password123" "uid=specialuser1,ou=specialusers,dc=example,dc=com"
----
+
This command should succeed.

. *Test Account Lockout for Special User*:
    .. Attempt to bind as `specialuser1` with incorrect passwords multiple times (more than `pwdMaxFailure` which is 2 for this policy).
    +
    [source,bash]
    ----
    ldapwhoami -x -D "uid=specialuser1,ou=specialusers,dc=example,dc=com" -w "wrongpass1"
    ldapwhoami -x -D "uid=specialuser1,ou=specialusers,dc=example,dc=com" -w "wrongpass2"
    ldapwhoami -x -D "uid=specialuser1,ou=specialusers,dc=example,dc=com" -w "wrongpass3" # This should trigger lockout
    ----
    +
    After the second failed attempt, the account should be locked. You'll observe the same lockout message as before, but it will be triggered more quickly due to the `pwdMaxFailure: 2` setting from the fine-grained policy.
    .. You can manually unlock `specialuser1` similar to `testuser1` by deleting `pwdAccountLockedTime`.

== Cleanup

To clean up your lab environment, you can remove the test users and the fine-grained password policy.

.Delete the test users:
+
[source,bash]
----
ldapdelete -x -D "cn=Directory Manager" -W "uid=testuser1,ou=users,dc=example,dc=com" -H ldapi:///
ldapdelete -x -D "cn=Directory Manager" -W "uid=specialuser1,ou=specialusers,dc=example,dc=com" -H ldapi:///
----

.Remove the `pwdPolicySubentry` from `ou=specialusers,dc=example,dc=com`:
+
[source,ldif]
----
dn: ou=specialusers,dc=example,dc=com
changetype: modify
delete: pwdPolicySubentry
----
+
Save this as `remove_fg_policy_link.ldif` and apply it:
+
[source,bash]
----
ldapmodify -x -D "cn=Directory Manager" -W -f remove_fg_policy_link.ldif -H ldapi:///
----

.Delete the `ou=specialusers,dc=example,dc=com` entry:
+
[source,bash]
----
ldapdelete -x -D "cn=Directory Manager" -W "ou=specialusers,dc=example,dc=com" -H ldapi:///
----

.Delete the fine-grained password policy definition:
+
[source,bash]
----
ldapdelete -x -D "cn=Directory Manager" -W "cn=SpecialUsersPolicy,cn=Password Policies,cn=config" -H ldapi:///
----

.Reset global password policies to default (optional, if you want to revert all changes):
+
[source,bash]
----
sudo dsconf -D "cn=Directory Manager" ldapi:/// _instance_name_ password policy set \
--min-length 0 \
--check-quality OFF \
--max-age 0 \
--expire-warning 0 \
--max-history 0 \
--max-failures 0 \
--failure-count-interval 0 \
--lockout-duration 0
----
+
*Note*: Setting values to `0` often means "no enforcement" or "use default" for certain password policy attributes. Some attributes like `pwdCheckQuality` require `ON`/`OFF`. Consult the official RHDS documentation for exact default behaviors.

== Conclusion

In this lab, you successfully configured and tested both global and fine-grained password policies in Red Hat Directory Server 13. You learned how to define rules for password complexity, aging, and account lockout at a global level, and then how to override these rules for specific organizational units by applying a more granular policy. This demonstrates the flexibility and control RHDS offers for securing user authentication.
