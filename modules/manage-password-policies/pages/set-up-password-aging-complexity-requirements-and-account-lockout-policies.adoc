#  Set up password aging, complexity requirements, and account lockout policies.

= Manage Password Policies: Aging, Complexity, and Account Lockout

Red Hat Directory Server (RHDS) provides robust mechanisms to enforce password policies, ensuring the security and integrity of user credentials. These policies are crucial for preventing unauthorized access, mitigating brute-force attacks, and maintaining compliance with security standards. RHDS allows administrators to define policies globally for all directory users or apply fine-grained policies to specific user groups or subtrees within the directory.

This section will delve into setting up and configuring three fundamental aspects of password policies: password aging, complexity requirements, and account lockout policies.

== Password Aging Policies

Password aging policies dictate how frequently users must change their passwords and prevent them from reusing old passwords. These policies are essential for reducing the risk associated with compromised credentials by ensuring passwords are regularly updated.

=== Concepts of Password Aging

RHDS uses several attributes to manage password aging:

*   `pwdMaxAge`: Specifies the maximum number of seconds a password can be used before it expires. After this period, the user will be prompted to change their password upon their next bind attempt.
*   `pwdMinAge`: Defines the minimum number of seconds that must elapse before a user can change their password again. This prevents users from immediately changing a new password back to an old one or another easily guessable password.
*   `pwdHistory`: Controls the number of previous passwords that the directory server remembers. Users are prevented from reusing any of these `pwdHistory` previous passwords when setting a new one.

=== Configuring Password Aging

Password aging policies can be configured globally or at a subtree level using LDIF files or the `dsconf` command-line utility.

==== Global Password Aging Policy

To configure a global password aging policy, modify the `cn=Password Policy,cn=config` entry.

.Example: Set Global Password Aging Policy
To set a password to expire after 90 days (7,776,000 seconds), enforce a minimum age of 1 day (86,400 seconds), and remember the last 5 passwords:

[source,bash]
----
dsconf -D "cn=Directory Manager" ldap://localhost:389 password policy set \
  pwdmaxage:7776000 \
  pwdminage:86400 \
  pwdhistory:5
----

Alternatively, you can use an LDIF file:

.pwd_aging.ldif
[source,ldif]
----
dn: cn=Password Policy,cn=config
changetype: modify
replace: pwdMaxAge
pwdMaxAge: 7776000
-
replace: pwdMinAge
pwdMinAge: 86400
-
replace: pwdHistory
pwdHistory: 5
----

Apply the LDIF file:

[source,bash]
----
ldapmodify -D "cn=Directory Manager" -w "your_password" -f pwd_aging.ldif
----

After setting these, users will be forced to change their password after 90 days, cannot change it again for 24 hours, and cannot reuse any of their last 5 passwords.

== Password Complexity Requirements

Password complexity policies ensure that users create strong, hard-to-guess passwords, significantly reducing the risk of dictionary attacks, brute-force attacks, and social engineering attempts.

=== Concepts of Password Complexity

RHDS offers a comprehensive set of attributes to define password complexity:

*   `pwdCheckQuality`: A critical attribute that controls the level of password quality checking.
    *   `0`: No checks performed (not recommended).
    *   `1`: Checks `pwdMinLength` and `pwdInHistory`.
    *   `2`: (Recommended) Performs comprehensive checks, including `pwdMinLength`, `pwdAlphabetical`, `pwdDigit`, `pwdSpecial`, `pwdCaseInsensitive`, `pwdDictionaryCheck`, and `pwdInHistory`.
*   `pwdMinLength`: The minimum number of characters required for a password.
*   `pwdAlphabetical`: The minimum number of alphabetical characters (a-z, A-Z) required.
*   `pwdDigit`: The minimum number of digit characters (0-9) required.
*   `pwdSpecial`: The minimum number of special characters (e.g., !, @, #, $, %, ^, &, *) required.
*   `pwdCaseInsensitive`: If set to `TRUE`, the password cannot be a case-insensitive match of the user's login ID or first/last name.
*   `pwdDictionaryCheck`: If set to `TRUE`, the password will be checked against a dictionary file (if configured) to prevent common words from being used.

[NOTE]
For `pwdDictionaryCheck` to be effective, a dictionary file needs to be configured. This is typically done by setting the `nsslapd-pwddict-path` attribute on the `cn=config` entry.

=== Configuring Password Complexity

==== Global Password Complexity Policy

To configure a global password complexity policy, modify the `cn=Password Policy,cn=config` entry.

.Example: Set Global Password Complexity Policy
To enforce passwords that are at least 12 characters long, contain at least 1 uppercase, 1 lowercase, 1 digit, and 1 special character, and enable comprehensive quality checks:

[source,bash]
----
dsconf -D "cn=Directory Manager" ldap://localhost:389 password policy set \
  pwdcheckquality:2 \
  pwdminlength:12 \
  pwdalphabetical:2 \
  pwddigit:1 \
  pwdspecial:1 \
  pwdcaseinsensitive:TRUE
----
(Note: `pwdalphabetical` accounts for both upper and lower case letters if `pwdCheckQuality=2`. If you want a specific number of *upper* case letters and *lower* case letters, you might need to use a custom password plugin or interpret `pwdalphabetical` as total letters and add logic.)

If you want a more precise control over uppercase/lowercase, the `pwdalphabetical` attribute in RHDS typically counts any letter. For distinct uppercase/lowercase requirements, you might need to leverage custom plugins or a combination of `pwdMinLength` and `pwdCheckQuality` with a strong interpretation. For simplicity, `pwdalphabetical:2` ensures at least two letters, leaving specific case counts to user discretion unless further policy is enforced. For strong policies, ensure total character count exceeds sum of type counts.

Alternatively, using an LDIF file:

.pwd_complexity.ldif
[source,ldif]
----
dn: cn=Password Policy,cn=config
changetype: modify
replace: pwdCheckQuality
pwdCheckQuality: 2
-
replace: pwdMinLength
pwdMinLength: 12
-
replace: pwdAlphabetical
pwdAlphabetical: 2
-
replace: pwdDigit
pwdDigit: 1
-
replace: pwdSpecial
pwdSpecial: 1
-
replace: pwdCaseInsensitive
pwdCaseInsensitive: TRUE
----

Apply the LDIF file:

[source,bash]
----
ldapmodify -D "cn=Directory Manager" -w "your_password" -f pwd_complexity.ldif
----

== Account Lockout Policies

Account lockout policies protect against brute-force attacks by temporarily disabling user accounts after a specified number of consecutive failed login attempts. This mechanism prevents attackers from repeatedly guessing passwords.

=== Concepts of Account Lockout

RHDS uses these attributes for account lockout:

*   `pwdLockout`: A boolean (`TRUE`/`FALSE`) attribute to enable or disable the account lockout feature.
*   `pwdMaxFailure`: The maximum number of consecutive failed bind attempts allowed before the account is locked.
*   `pwdFailureCountInterval`: The time interval (in seconds) during which failed login attempts are counted. If a user tries to bind successfully within this interval after some failures, the failure count is reset.
*   `pwdLockoutDuration`: The duration (in seconds) for which an account remains locked after `pwdMaxFailure` attempts. If set to `0`, the account remains locked indefinitely until an administrator manually unlocks it.

=== Configuring Account Lockout

==== Global Account Lockout Policy

To configure a global account lockout policy, modify the `cn=Password Policy,cn=config` entry.

.Example: Set Global Account Lockout Policy
To enable account lockout, lock an account after 5 failed attempts within 300 seconds (5 minutes), and keep it locked for 900 seconds (15 minutes):

[source,bash]
----
dsconf -D "cn=Directory Manager" ldap://localhost:389 password policy set \
  pwdlockout:TRUE \
  pwdmaxfailure:5 \
  pwdfailurecountinterval:300 \
  pwdlockoutduration:900
----

Alternatively, using an LDIF file:

.pwd_lockout.ldif
[source,ldif]
----
dn: cn=Password Policy,cn=config
changetype: modify
replace: pwdLockout
pwdLockout: TRUE
-
replace: pwdMaxFailure
pwdMaxFailure: 5
-
replace: pwdFailureCountInterval
pwdFailureCountInterval: 300
-
replace: pwdLockoutDuration
pwdLockoutDuration: 900
----

Apply the LDIF file:

[source,bash]
----
ldapmodify -D "cn=Directory Manager" -w "your_password" -f pwd_lockout.ldif
----

[TIP]
To manually unlock an account that is locked indefinitely (`pwdLockoutDuration: 0`), an administrator can set the `pwdAccountLockedTime` attribute for the user's entry to `000001010000Z` (or remove it entirely).

== Fine-Grained Password Policies (FGPP)

While global policies apply to all users, RHDS also supports Fine-Grained Password Policies (FGPPs) or subtree-level password policies. These allow different password policies for different groups of users or OUs. This is achieved by creating new `cn=Password Policy,cn=<policy_name>,cn=config` entries and applying them to specific subtrees using the `pwdPolicySubentry` attribute on the target OU.

[NOTE]
Fine-grained password policies are advanced configurations and are covered in more detail in the 'Manage Password Policies' Hands-on Lab. The examples here focus on global policies for clarity.

== Hands-on Lab: Configure and Test Password Policies

This lab guides you through configuring global password aging, complexity, and account lockout policies and then testing their enforcement.

=== Lab Environment Setup

Ensure you have a running Red Hat Directory Server 13 instance. If not, refer to the "Install and Configure Red Hat Directory Server 13" module to deploy one.

==== Prerequisites

*   A running RHDS instance.
*   `ldapsearch`, `ldapadd`, `ldapmodify`, `dsconf` utilities available.
*   `cn=Directory Manager` credentials.

==== Create a Test User

First, create a user account for testing the policies.

.Create a new test user `testuser1`
[source,bash]
----
ldapadd -D "cn=Directory Manager" -w "your_directory_manager_password" <<EOF
dn: uid=testuser1,ou=users,dc=example,dc=com
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: testuser1
cn: Test User 1
sn: User1
userPassword: password
EOF
----
[NOTE]
Replace `dc=example,dc=com` with your directory's base DN and `your_directory_manager_password` with the actual password.

.Verify the user creation
[source,bash]
----
ldapsearch -D "cn=Directory Manager" -w "your_directory_manager_password" -b "uid=testuser1,ou=users,dc=example,dc=com" uid
----
Expected output should show `uid: testuser1`.

=== Task 1: Configure Password Aging Policy

In this task, you will configure a global password aging policy. For testing purposes, we'll set short intervals.

.Configure Global Password Aging
Set `pwdMaxAge` to 300 seconds (5 minutes), `pwdMinAge` to 60 seconds (1 minute), and `pwdHistory` to 2.

[source,bash]
----
dsconf -D "cn=Directory Manager" ldap://localhost:389 password policy set \
  pwdmaxage:300 \
  pwdminage:60 \
  pwdhistory:2
----

.Verify Password Aging Configuration
[source,bash]
----
ldapsearch -D "cn=Directory Manager" -w "your_directory_manager_password" -b "cn=Password Policy,cn=config" \
  pwdMaxAge pwdMinAge pwdHistory
----
Confirm that the attributes reflect the values you set.

.Test Password Aging
Login with `testuser1`. This initial bind will set the `pwdChangedTime`.
[source,bash]
----
ldapwhoami -D "uid=testuser1,ou=users,dc=example,dc=com" -w "password"
----
Wait for 300 seconds (5 minutes) for the password to expire.

Attempt to bind again after 5 minutes. You should receive an `LDAP_CONSTRAINT_VIOLATION` or a similar error indicating the password has expired and needs to be changed.
[source,bash]
----
ldapwhoami -D "uid=testuser1,ou=users,dc=example,dc=com" -w "password"
----
Now, try to change the password:
[source,bash]
----
ldappasswd -D "uid=testuser1,ou=users,dc=example,dc=com" -w "password" -s "newpassword1"
----
It should succeed.

Wait for 60 seconds (1 minute). Now, try to change the password again to `newpassword2`.
[source,bash]
----
ldappasswd -D "uid=testuser1,ou=users,dc=example,dc=com" -w "newpassword1" -s "newpassword2"
----
This should succeed.

Now try to change the password back to `password` (one of the last 2 passwords in history).
[source,bash]
----
ldappasswd -D "uid=testuser1,ou=users,dc=example,dc=com" -w "newpassword2" -s "password"
----
This should *fail* with an `LDAP_CONSTRAINT_VIOLATION` error, indicating it's in the password history.

=== Task 2: Configure Password Complexity Policy

Now, configure complexity requirements for passwords.

.Configure Global Password Complexity
Set `pwdCheckQuality:2`, `pwdMinLength:8`, `pwdAlphabetical:1`, `pwdDigit:1`, `pwdSpecial:1`.

[source,bash]
----
dsconf -D "cn=Directory Manager" ldap://localhost:389 password policy set \
  pwdcheckquality:2 \
  pwdminlength:8 \
  pwdalphabetical:1 \
  pwddigit:1 \
  pwdspecial:1
----

.Verify Password Complexity Configuration
[source,bash]
----
ldapsearch -D "cn=Directory Manager" -w "your_directory_manager_password" -b "cn=Password Policy,cn=config" \
  pwdCheckQuality pwdMinLength pwdAlphabetical pwdDigit pwdSpecial
----
Confirm the values are set correctly.

.Test Password Complexity
Attempt to change `testuser1`'s password to a simple password (e.g., `testpass`). This should fail.
[source,bash]
----
ldappasswd -D "uid=testuser1,ou=users,dc=example,dc=com" -w "newpassword2" -s "testpass"
----
Expected error: `LDAP_CONSTRAINT_VIOLATION` for password complexity.

Now, try changing the password to one that meets the complexity requirements (e.g., `P@ssword1`).
[source,bash]
----
ldappasswd -D "uid=testuser1,ou=users,dc=example,dc=com" -w "newpassword2" -s "P@ssword1"
----
This should succeed.

=== Task 3: Configure Account Lockout Policy

Finally, configure and test account lockout.

.Configure Global Account Lockout
Set `pwdLockout:TRUE`, `pwdMaxFailure:3`, `pwdFailureCountInterval:120` (2 minutes), `pwdLockoutDuration:300` (5 minutes).

[source,bash]
----
dsconf -D "cn=Directory Manager" ldap://localhost:389 password policy set \
  pwdlockout:TRUE \
  pwdmaxfailure:3 \
  pwdfailurecountinterval:120 \
  pwdlockoutduration:300
----

.Verify Account Lockout Configuration
[source,bash]
----
ldapsearch -D "cn=Directory Manager" -w "your_directory_manager_password" -b "cn=Password Policy,cn=config" \
  pwdLockout pwdMaxFailure pwdFailureCountInterval pwdLockoutDuration
----
Confirm the values.

.Test Account Lockout
Attempt to bind as `testuser1` with an incorrect password more than `pwdMaxFailure` (3) times.

[source,bash]
----
ldapwhoami -D "uid=testuser1,ou=users,dc=example,dc=com" -w "wrongpass" # Attempt 1
ldapwhoami -D "uid=testuser1,ou=users,dc=example,dc=com" -w "wrongpass" # Attempt 2
ldapwhoami -D "uid=testuser1,ou=users,dc=example,dc=com" -w "wrongpass" # Attempt 3
----
After the third attempt, the user account should be locked. You should see an `LDAP_CONSTRAINT_VIOLATION` error or similar, indicating the account is locked.

.Verify User Lockout Status
[source,bash]
----
ldapsearch -D "cn=Directory Manager" -w "your_directory_manager_password" -b "uid=testuser1,ou=users,dc=example,dc=com" \
  pwdAccountLockedTime pwdFailureTime pwdGraceUseTime
----
You should see `pwdAccountLockedTime` with a timestamp, indicating the account is locked.

Wait for `pwdLockoutDuration` (300 seconds or 5 minutes) to pass.
After 5 minutes, attempt to bind with the correct password (`P@ssword1`).
[source,bash]
----
ldapwhoami -D "uid=testuser1,ou=users,dc=example,dc=com" -w "P@ssword1"
----
This bind should now succeed, as the account has automatically unlocked.

If `pwdLockoutDuration` was set to `0`, the account would remain locked indefinitely. To unlock it manually:

[source,bash]
----
# Replace 'uid=testuser1,ou=users,dc=example,dc=com' with the user's DN
ldapmodify -D "cn=Directory Manager" -w "your_directory_manager_password" <<EOF
dn: uid=testuser1,ou=users,dc=example,dc=com
changetype: modify
delete: pwdAccountLockedTime
EOF
----
Then, verify the `pwdAccountLockedTime` attribute is no longer present.

This lab demonstrates the successful configuration and testing of global password aging, complexity, and account lockout policies in Red Hat Directory Server 13. These fundamental security measures are critical for maintaining a robust and secure directory environment.
