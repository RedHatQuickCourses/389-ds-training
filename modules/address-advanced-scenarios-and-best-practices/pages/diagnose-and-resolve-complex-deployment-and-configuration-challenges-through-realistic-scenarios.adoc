#  Diagnose and resolve complex deployment and configuration challenges through realistic scenarios.

= Diagnose and Resolve Complex Deployment and Configuration Challenges

In enterprise environments, Red Hat Directory Server (RHDS) deployments can become intricate, involving multiple instances, replication topologies, stringent security policies, and integrations with various applications. While basic installation and configuration are straightforward, complex challenges often arise from misconfigurations, resource constraints, network issues, or unanticipated interactions between different components. This section delves into common complex scenarios, providing diagnostic strategies and resolution techniques.

== Common Complex Challenges in RHDS Deployments

Understanding the common categories of complex issues can help administrators anticipate and quickly diagnose problems. These often span across performance, replication, security, and schema management.

=== Performance Degradation Under Load

*   **Symptoms:** Slow search queries, high CPU/memory usage on the directory server, client applications timing out, overall system sluggishness.
*   **Causes:**
    *   **Missing or inefficient indexes:** Searching on unindexed attributes can be extremely slow, especially in large directories.
    *   **Inefficient search filters:** Clients performing broad or poorly constructed searches.
    *   **Insufficient hardware resources:** CPU, RAM, or I/O bottlenecks.
    *   **Database caching issues:** Cache sizes not optimized for the dataset and workload.
    *   **Network latency:** Slow network between clients and the server.
    *   **Verbose logging levels:** Excessive logging can impact I/O performance.

=== Replication Failures and Lag

*   **Symptoms:** Directory data not synchronizing between servers, `dsctl replication status` showing errors or stale entries, different data on different replicas, applications failing to retrieve consistent information.
*   **Causes:**
    *   **Network connectivity issues:** Firewalls blocking replication ports, network latency, packet loss.
    *   **Schema conflicts:** Different schemas on replication partners, leading to entry rejection.
    *   **Insufficient disk space:** Replication updates cannot be written.
    *   **Replication queue overflow:** Too many changes accumulated, overwhelming the consumer.
    *   **Incorrect replication agreement configuration:** Misconfigured bind DNs, passwords, or replication ports.
    *   **Time drift:** Significant time difference between replication partners (critical for Change Sequence Numbers - CSN).
    *   **Server resource exhaustion:** Slow I/O, CPU, or memory on a replica.

=== Authentication and Authorization Failures

*   **Symptoms:** Users unable to bind or access specific directory entries, applications receiving "Insufficient access" or "Invalid credentials" errors despite correct credentials, inconsistent access for users across different applications.
*   **Causes:**
    *   **Misconfigured Access Control Instructions (ACIs):** Complex ACI rules interacting unexpectedly, blocking legitimate access, or granting unintended access.
    *   **Incorrect bind DNs or passwords:** Applications attempting to bind with stale or incorrect credentials.
    *   **TLS/SSL certificate issues:** Expired certificates, untrusted CAs, misconfigured `certmap.conf` for client certificate authentication.
    *   **Password policy conflicts:** Global vs. fine-grained policies leading to unexpected password requirements or account lockouts.
    *   **Incorrect SASL mapping:** When using SASL mechanisms like GSSAPI, incorrect principal mappings can cause authentication failures.

=== Schema Conflicts and Customizations

*   **Symptoms:** Errors when adding entries with custom attributes/object classes, `LDAP_OBJECT_CLASS_VIOLATION` or `LDAP_ATTRIBUTE_OR_VALUE_EXISTS` during data import, applications failing to store specific data.
*   **Causes:**
    *   **Custom schema not correctly deployed:** LDIF files for new object classes/attributes not imported, or imported into the wrong suffix.
    *   **Conflicting OIDs:** Custom schema using OIDs already in use by standard schema or other custom schema.
    *   **Syntax violations:** Attributes defined with incorrect syntaxes or matching rules.
    *   **Schema replication issues:** Custom schema not replicating correctly to all instances.

== Diagnostic Tools and Techniques

Effective troubleshooting relies on systematic diagnosis using the right tools.

*   **RHDS Specific Utilities:**
    *   `dsctl`: For server status, replication status, and instance lifecycle management.
    *   `dsconf`: For configuration management, including replication agreements, plugins, and server settings.
    *   `dsidm`: For managing instances, suffixes, and certain database properties.
    *   `ldapsearch`, `ldapadd`, `ldapmodify`, `ldapdelete`: Standard OpenLDAP client tools for data manipulation and verification.
    *   `dscreate`: For instance creation.
    *   `certutil`: For managing NSS databases and certificates.
*   **Log Files:**
    *   `/var/log/dirsrv/slapd-INSTANCE_NAME/errors`: Primary log for server errors, warnings, and replication issues.
    *   `/var/log/dirsrv/slapd-INSTANCE_NAME/access`: Records client operations, useful for debugging authentication and authorization.
    *   `audit` logs (if enabled): Detailed record of administrative changes and sensitive operations.
*   **System Monitoring Tools:**
    *   `top`, `htop`: For real-time CPU and memory usage.
    *   `iostat`, `vmstat`: For I/O performance.
    *   `netstat`, `ss`: For network connections and port status.
    *   `journalctl -u dirsrv@INSTANCE_NAME.service`: For service-level logs and startup issues.

== Hands-on Lab: Diagnose and Resolve Complex RHDS Challenges

This lab presents realistic scenarios and guides you through diagnosing and resolving them.

=== Scenario 1: Intermittent Replication Lag and Conflicts

You have a multi-supplier replication topology between `server1.example.com` (Supplier A) and `server2.example.com` (Supplier B). Users report that changes made on one server are not always immediately visible on the other, or worse, some updates seem to be lost.

**Problem Statement:** Replication lag and potential conflicts in a multi-supplier setup.

**Symptoms:**
*   `ldapsearch` on `server1` shows a user's updated attribute, but `ldapsearch` on `server2` shows the old value.
*   `dsctl replication status` might show `window_status: error` or `last_update_status` indicating delays.
*   Error messages in `/var/log/dirsrv/slapd-INSTANCE_NAME/errors` on one or both servers related to replication.

**Technical Explanation:** Replication relies on Change Sequence Numbers (CSNs) and timestamps. Lag often points to network issues, resource bottlenecks, or problems with the replication agreement itself. Conflicts can arise in multi-supplier if the same entry is modified concurrently on both servers without proper conflict resolution mechanisms (though RHDS has built-in conflict resolution based on CSN timestamps, excessive conflicts can indicate deeper issues).

**Lab Steps:**

.  **Verify Service Status:**
    Ensure both RHDS instances are running correctly.
    [source,bash]
    ----
    # On server1
    sudo dsctl status INSTANCE_NAME

    # On server2
    sudo dsctl status INSTANCE_NAME
    ----

.  **Check Replication Status:**
    Use `dsctl replication status` to get an overview.
    [source,bash]
    ----
    # On server1, check status with server2 as consumer
    sudo dsctl replication status INSTANCE_NAME -s server2.example.com

    # On server2, check status with server1 as consumer
    sudo dsctl replication status INSTANCE_NAME -s server1.example.com
    ----
    Look for:
    *   `last_update_status`: Should be "Success".
    *   `lag`: Should be low or zero.
    *   `window_status`: Should be "OK".
    *   `replica_last_update_csn`: Compare across servers to see if they are close.

.  **Examine Error Logs:**
    Review the `errors` log on both servers for replication-related messages.
    [source,bash]
    ----
    # On both servers
    sudo tail -f /var/log/dirsrv/slapd-INSTANCE_NAME/errors | grep -i replication
    ----
    Look for:
    *   `Entry (cn=user,ou=people,dc=example,dc=com) could not be added because an entry with the same DN already exists`
    *   `Connection error` messages.
    *   `Error adding change to replica`

.  **Check Network Connectivity:**
    Ensure replication ports (default 389 for LDAP, 636 for LDAPS) are open and reachable between servers.
    [source,bash]
    ----
    # On server1, test connection to server2's LDAP port
    nc -vz server2.example.com 389

    # On server2, test connection to server1's LDAP port
    nc -vz server1.example.com 389
    ----
    Verify firewall rules if connections fail.

.  **Verify Replication Agreement Configuration:**
    Ensure the replication agreements are correctly configured, specifically the bind DN and password. A common mistake is using an incorrect password or a bind DN that doesn't have replication update permissions.
    [source,bash]
    ----
    # On server1 (as an example for server2 as consumer)
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 replication list -P server2.example.com -S dc=example,dc=com

    # You can also dump the agreement details
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 replication info -P server2.example.com -S dc=example,dc=com --suffix "dc=example,dc=com" --agreement AGREEMENT_NAME
    ----
    Pay attention to `nsDS5ReplicaBindDN` and ensure the password is correct using `dsconf replication set-passwd`.

.  **Check Time Synchronization:**
    Discrepancies in system time can cause CSN issues.
    [source,bash]
    ----
    # On both servers
    timedatectl status
    ----
    Ensure NTP is configured and working on both servers.

.  **Monitor System Resources:**
    High CPU, memory, or disk I/O on one server can slow down replication.
    [source,bash]
    ----
    # On both servers
    top
    iostat -x 1 10
    ----

**Resolution Steps (Example based on common findings):**

*   **Firewall blocking:** Open necessary ports (e.g., 389, 636) in the firewall.
    [source,bash]
    ----
    sudo firewall-cmd --permanent --add-port=389/tcp
    sudo firewall-cmd --permanent --add-port=636/tcp
    sudo firewall-cmd --reload
    ----
*   **Incorrect bind password:** Update the replication agreement password.
    [source,bash]
    ----
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 replication set-passwd -P server2.example.com -S dc=example,dc=com --agreement AGREEMENT_NAME
    # You will be prompted for the old and new password
    ----
*   **Time drift:** Configure and enable NTP.
    [source,bash]
    ----
    sudo dnf install -y ntp
    sudo systemctl enable ntpd --now
    ----
    *After resolving underlying issues, you might need to re-initialize the replica if the lag is too severe or the data divergent. This is a last resort and should be done during a maintenance window.*
    [source,bash]
    ----
    # On the lagging consumer (server2), stop replication, re-initialize from supplier (server1)
    sudo dsctl stop INSTANCE_NAME
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 replication initialize -S dc=example,dc=com --agreement AGREEMENT_NAME
    sudo dsctl start INSTANCE_NAME
    ----
    *Make sure to understand the impact of re-initialization before performing it, as it will overwrite the consumer's suffix data with that from the supplier.*

=== Scenario 2: Slow Search Performance and High Server Load

Users are reporting that LDAP-backed applications are slow to respond, and the RHDS server's CPU usage is consistently high during peak hours. You suspect search operations are inefficient.

**Problem Statement:** Poor search performance leading to high CPU load.

**Symptoms:**
*   Applications experience delays when querying the directory.
*   `top` command on the RHDS server shows high CPU usage by `ns-slapd`.
*   `access` logs show search operations with long `etime` (elapsed time).

**Technical Explanation:** The most common cause of slow search performance in RHDS is the lack of proper attribute indexing. When an attribute is not indexed, the directory server must perform a full scan of the database to find matching entries, which is highly inefficient for large directories.

**Lab Steps:**

.  **Monitor Server Load:**
    Observe the server's CPU and memory usage using `top`.
    [source,bash]
    ----
    top
    ----
    Identify if `ns-slapd` is the primary consumer of resources.

.  **Analyze Access Logs for Slow Searches:**
    Configure detailed access logging if not already enabled. Then, filter the `access` log for slow search operations.
    [source,bash]
    ----
    # Ensure detailed access logging is enabled (if not, configure via dsconf)
    # sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 set-log-level access on
    # sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 set-log-parameter -P access accesslog-level 65536

    # Watch for slow searches (search operations with high etime)
    sudo grep 'SRCH etime=' /var/log/dirsrv/slapd-INSTANCE_NAME/access | awk '$5 ~ /etime=[0-9]+$/ {print $0}' | sort -k5nr | head -n 20
    ----
    This command filters for search entries, extracts the `etime` (elapsed time), sorts by it in reverse numerical order, and shows the 20 slowest searches. Identify the attributes being used in the search filters (e.g., `(uid=john.doe)`, `(mail=*@example.com)`).

.  **Check Existing Indexes:**
    List the indexes configured for your suffix.
    [source,bash]
    ----
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 index list -S dc=example,dc=com
    ----
    Compare the attributes used in the slow search filters with the listed indexes. If an attribute from a slow search is not indexed, or only has a `pres` (presence) index, it's a strong candidate for a new index. For attributes used with equality searches (e.g., `(uid=john.doe)`), an `eq` (equality) index is usually needed. For substring searches (e.g., `(mail=*@example.com)`), a `sub` (substring) index might be beneficial, but these are more resource-intensive.

**Resolution Steps:**

*   **Add Missing Indexes:**
    Based on the slow searches identified in the `access` logs, add the appropriate indexes. Let's assume `employeeNumber` is being used frequently in equality searches and is unindexed.
    [source,bash]
    ----
    # Add an equality index for 'employeeNumber'
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 index add -S dc=example,dc=com --attr employeeNumber --type eq

    # Verify the index was added
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 index list -S dc=example,dc=com | grep employeeNumber
    ----

*   **Rebuild Indexes:**
    After adding a new index (or if an existing index is suspected to be corrupted), you must rebuild it. This can be a resource-intensive operation and may take time for very large databases.
    [source,bash]
    ----
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 index rebuild -S dc=example,dc=com --attr employeeNumber
    ----
    Monitor the server load during the rebuild process.

*   **Optimize Database Caches:**
    If indexing doesn't fully resolve the issue, consider optimizing the database cache sizes, especially `nsslapd-cache-attr-enabled` and `nsslapd-cache-memlimit`. These settings are instance-specific and can be tuned based on available RAM and directory size.
    [source,bash]
    ----
    # Example: Set a larger database cache size (adjust based on RAM)
    # For a server with 16GB RAM, 4GB for cache might be reasonable.
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 set-suffix-prop dc=example,dc=com nsslapd-cache-memlimit=4GB

    # This requires a server restart to take full effect.
    sudo dsctl restart INSTANCE_NAME
    ----

*   **Review Application Search Filters:**
    Sometimes the problem lies with inefficient search filters used by client applications. Work with application developers to optimize their LDAP queries (e.g., avoid wildcards at the beginning of attributes unless strictly necessary, narrow down base DNs).

=== Scenario 3: Granular Access Control (ACI) Denials

An application (or a specific user binding as `appuser`) is configured to update only certain attributes (`telephoneNumber`, `mobile`) for users in the `ou=people,dc=example,dc=com` branch, but it's receiving "Insufficient access" errors. Other attributes are not intended to be modifiable by this application.

**Problem Statement:** Application unable to modify specific user attributes due to ACI misconfiguration, while overall access is too broad.

**Symptoms:**
*   Application logs show `LDAP_INSUFFICIENT_ACCESS` or `LDAP_CONSTRAINT_VIOLATION` when attempting to modify attributes.
*   `access` logs on the RHDS server show operations failing with `err=50` (Insufficient access).
*   Even with correct credentials, the application cannot perform the intended operation.

**Technical Explanation:** ACIs are powerful but complex. They are evaluated in a specific order, and the most specific `deny` rule often takes precedence over a more general `allow` rule. A common issue is a general `deny` rule inadvertently blocking more specific `allow` rules, or insufficient permissions on the specific attributes/entries.

**Lab Steps:**

.  **Identify the Failing Operation and Bind DN:**
    From the application or `access` logs, identify:
    *   The exact `dn` of the entry being modified.
    *   The specific attribute(s) being modified.
    *   The `binddn` used by the application (e.g., `cn=appuser,ou=applications,dc=example,dc=com`).
    *   The `IP address` of the client application.

    Example `access` log entry for a failed modify:
    [source,text]
    ----
    [01/Jan/2024:10:30:05.123456 -0500] conn=123 op=5 MOD dn="uid=john.doe,ou=people,dc=example,dc=com"
    [01/Jan/2024:10:30:05.123500 -0500] conn=123 op=5 RESULT err=50 tag=103 nentries=0 etime=0.000000 client="192.168.1.10" dn="cn=appuser,ou=applications,dc=example,dc=com"
    ----

.  **Review Existing ACIs:**
    Dump all ACIs for the relevant suffix.
    [source,bash]
    ----
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 aci list -S dc=example,dc=com
    ----
    This will show all ACIs. It can be a lot. Alternatively, you can use `ldapsearch` to retrieve `aci` attributes:
    [source,bash]
    ----
    ldapsearch -x -D "cn=Directory Manager" -W -b "dc=example,dc=com" -s sub "(objectclass=*)" aci
    ----
    Look for ACIs that mention the bind DN (`cn=appuser,...`), the target DN (`uid=john.doe,...`), or the specific attributes (`telephoneNumber`, `mobile`). Pay close attention to `allow` and `deny` rules, and their order/specificity.

.  **Test ACI Evaluation with `ldapmodify`:**
    Attempt the exact `ldapmodify` operation that failed from the application, but using `ldapmodify` directly. This helps isolate if it's an ACI issue or an application-specific problem.
    [source,bash]
    ----
    # Example LDIF for modification
    cat << EOF > /tmp/modify_user.ldif
    dn: uid=john.doe,ou=people,dc=example,dc=com
    changetype: modify
    replace: telephoneNumber
    telephoneNumber: +1 555 123 4567
    -
    replace: mobile
    mobile: +1 555 987 6543
    EOF

    # Attempt modification as the application user
    ldapmodify -x -D "cn=appuser,ou=applications,dc=example,dc=com" -W -f /tmp/modify_user.ldif
    ----
    If this also fails with `Insufficient access`, the ACI is indeed the problem.

**Resolution Steps (Example):**

Let's assume the current ACIs were too restrictive or missing the specific permission.
We want to achieve: `cn=appuser,...` can modify `telephoneNumber` and `mobile` on entries under `ou=people,dc=example,dc=com`.

*   **Add a Specific ACI for the Application User:**
    Create an ACI that grants the specific permissions needed.
    [source,bash]
    ----
    sudo dsconf -D "cn=Directory Manager" ldap://localhost:389 aci add -S dc=example,dc=com \
      --bind-dn "cn=appuser,ou=applications,dc=example,dc=com" \
      --target-attr "telephoneNumber || mobile" \
      --target-scope "subtree" \
      --target-filter "(objectclass=inetorgperson)" \
      --access "write" \
      --base "ou=people,dc=example,dc=com" \
      --desc "Allow appuser to modify phone numbers for people"
    ----
    *   `--bind-dn`: Specifies who is allowed (`cn=appuser,...`).
    *   `--target-attr`: Specifies *which* attributes can be modified.
    *   `--target-scope "subtree"`: Applies to all entries under `--base`.
    *   `--target-filter "(objectclass=inetorgperson)"`: Limits to specific object classes (optional but good practice).
    *   `--access "write"`: Grants write permission.
    *   `--base`: The root of the scope for this ACI.

*   **Test the New ACI:**
    Repeat step 3 from the diagnostic steps with `ldapmodify` using the application's bind DN. The operation should now succeed.
    [source,bash]
    ----
    ldapmodify -x -D "cn=appuser,ou=applications,dc=example,dc=com" -W -f /tmp/modify_user.ldif
    ----
    Check the `access` logs for `err=0` (Success).

**Tips for ACI Troubleshooting:**

*   **Keep ACIs simple:** Overly complex ACIs are prone to errors.
*   **Test incrementally:** Add one ACI at a time and test its effect.
*   **Understand precedence:** `deny` rules generally override `allow` rules when they apply to the same scope. The most specific rule wins.
*   **Use `aci-evaluate` tool (if available in your RHDS version or a similar utility):** Some tools can simulate ACI evaluation. While not a standard `dsconf` command, it's a concept to look for in advanced debugging.
*   **Check inherited ACIs:** ACIs can be inherited from parent entries or the suffix root.

By systematically diagnosing and resolving these complex scenarios, you build a robust understanding of Red Hat Directory Server's internal workings and troubleshooting methodologies. Remember to always test changes in a non-production environment first and have a rollback plan.
