== 1. Optimizing Search Performance with Attribute Indexing

Attribute indexing is a fundamental technique for improving the efficiency of search operations in Red Hat Directory Server. Without appropriate indexes, the server must perform a full scan of all entries within a suffix to find matches, which can be extremely slow for large directories and consume significant CPU and I/O resources.

=== 1.1. Understanding LDAP Indexes

An LDAP index is analogous to an index in a traditional relational database. It provides a quick lookup mechanism for specific attribute values, allowing the directory server to rapidly locate entries that match a search filter without scanning every single entry.

RHDS supports several types of indexes, each optimized for different search filter operations:

*   **Equality Index (`eq`):** Used for exact match searches (e.g., `(uid=jdoe)`). This is the most common and generally most important index type.
*   **Presence Index (`pres`):** Used to determine if an attribute exists in an entry (e.g., `(mail=*)`).
*   **Substring Index (`sub`):** Used for searches involving partial string matches (e.g., `(cn=*john*)`). These are more resource-intensive to maintain and query but essential for wildcard searches.
*   **Approximate Index (`approx`):** Used for "sounds like" searches (e.g., `(sn~=smith)`). Less commonly used.
*   **Virtual List View (VLV) Index (`vlv`):** Used for specific client applications that require sorted and paginated views of directory entries.

For optimal performance, you should identify attributes frequently used in search filters and configure appropriate indexes for them. Over-indexing, however, can also have a negative impact as each index adds overhead during write operations (add, modify, delete).

=== 1.2. Hands-on Activity: Configuring and Testing Attribute Indexes

In this activity, you will:
1.  Add some sample data to your directory.
2.  Perform a search on an unindexed attribute to observe its baseline performance.
3.  Add an equality index for that attribute.
4.  Rebuild the index.
5.  Perform the same search again and compare the performance improvement.

Let's assume your RHDS instance is named `instance1` and listens on `localhost:389`.

.Procedure

.  *Verify current indexes for an attribute (Optional)*
    First, let's see what indexes (if any) are configured for a common attribute like `givenName` in the `userRoot` suffix.

    ```bash
    dsconf -D "cn=Directory Manager" ldap://localhost:389 index list --suffix userRoot --attr givenName
    ```

    You'll likely see something like `No index configuration for attribute givenName.`

.  *Add sample user data*
    Let's add a few users, ensuring one has a `givenName` we'll search for. Create a file named `users.ldif`:

    ```ldif
    dn: uid=jane.doe,ou=People,dc=example,dc=com
    objectClass: top
    objectClass: person
    objectClass: organizationalPerson
    objectClass: inetOrgPerson
    uid: jane.doe
    cn: Jane Doe
    sn: Doe
    givenName: Jane
    mail: jane.doe@example.com
    userPassword: password

    dn: uid=john.smith,ou=People,dc=example,dc=com
    objectClass: top
    objectClass: person
    objectClass: organizationalPerson
    objectClass: inetOrgPerson
    uid: john.smith
    cn: John Smith
    sn: Smith
    givenName: John
    mail: john.smith@example.com
    userPassword: password
    ```

    Now, add these entries to your directory. Replace `dc=example,dc=com` with your base DN if different.

    ```bash
    ldapadd -x -D "cn=Directory Manager" -w password -f users.ldif -H ldap://localhost:389
    ```
    *Expected output:*
    ```
    adding new entry "uid=jane.doe,ou=People,dc=example,dc=com"
    adding new entry "uid=john.smith,ou=People,dc=example,dc=com"
    ```

.  *Perform a search on an unindexed attribute and measure time*
    We'll search for `givenName=Jane` and measure how long it takes. For accurate timing, repeat the search several times.

    ```bash
    time ldapsearch -x -D "cn=Directory Manager" -w password -b "ou=People,dc=example,dc=com" "(givenName=Jane)" givenName sn
    ```
    Note the `real` time from the `time` command output. This is your baseline. With only a few entries, the difference might be negligible, but it scales significantly with data.

.  *Add an equality index for `givenName`*
    We will now add an equality index for the `givenName` attribute on the `userRoot` suffix using `dsconf`.

    ```bash
    dsconf -D "cn=Directory Manager" ldap://localhost:389 index add --suffix userRoot --attr givenName --index-type eq
    ```
    *Expected output:*
    ```
    Successfully added index 'eq' to attribute 'givenName' in suffix 'userRoot'.
    ```

.  *Rebuild the attribute index*
    After adding a new index or modifying an existing one, you *must* rebuild the index database for the changes to take effect on existing data. This is a critical step.

    ```bash
    dsctl instance1 db rebuild-index userRoot
    ```
    *Expected output (might take some time for large directories):*
    ```
    Index rebuild started for 'userRoot' suffix...
    Index rebuild completed for 'userRoot' suffix.
    ```
    You can monitor the rebuild process by checking the server logs (`/var/log/dirsrv/slapd-instance1/errors`).

.  *Perform the search again and compare performance*
    Execute the same search command for `givenName=Jane` and compare the `real` time.

    ```bash
    time ldapsearch -x -D "cn=Directory Manager" -w password -b "ou=People,dc=example,dc=com" "(givenName=Jane)" givenName sn
    ```

    You should observe a measurable improvement, especially if you had a large dataset. The server logs can also provide insights into whether indexes were used in a search operation (look for `SRCH` entries).

.  *Verify the configured index*
    You can confirm the index has been applied using `dsconf`:

    ```bash
    dsconf -D "cn=Directory Manager" ldap://localhost:389 index list --suffix userRoot --attr givenName
    ```
    *Expected output:*
    ```
    Index configuration for attribute givenName in suffix userRoot:
    - Index type: eq
    ```

[NOTE]
====
For a real-world scenario with millions of entries, the performance difference between an indexed and unindexed search can be orders of magnitude, turning a multi-second or multi-minute operation into a sub-second one.
====

=== 1.3. Expert Tip: When to Index

*   **Index frequently searched attributes:** Any attribute used in `(attribute=value)` filters should ideally have an `eq` index.
*   **Consider substring indexes carefully:** `sub` indexes are useful for wildcard searches (e.g., `(cn=*john*)`) but consume more disk space and can slow down write operations. Only add them for attributes frequently used in such searches.
*   **Avoid over-indexing:** Every index adds overhead to entry additions, modifications, and deletions. Only index attributes that genuinely benefit search performance.
*   **Monitor your logs:** The RHDS error log can provide hints about inefficient searches that might benefit from indexing. Look for messages related to "unindexed searches."

== 2. Extending Functionality with RHDS Plugins

Red Hat Directory Server's architecture is highly extensible through the use of plugins. Plugins are dynamically loadable modules that allow administrators to add new features, enforce policies, and customize server behavior without modifying the core server code. This modularity makes RHDS incredibly flexible.

=== 2.1. Understanding RHDS Plugins

Plugins can intercept and modify nearly any operation performed by the directory server, from client authentication to data manipulation and replication. They can be broadly categorized by their function:

*   **Operation Plugins:** Intercept LDAP operations (bind, add, modify, search, delete) to enforce policies or trigger actions. Examples include password policy, unique attribute, and referential integrity plugins.
*   **Database Plugins:** Interact directly with the directory's database backend, often used for custom data storage or indexing.
*   **Replication Plugins:** Handle replication logic between directory servers.
*   **Monitoring Plugins:** Collect performance metrics and statistics.

Plugins are crucial for implementing many advanced features, such as:

*   **Password Policy Enforcement:** Ensuring strong, complex, and aging passwords.
*   **Referential Integrity:** Maintaining consistency of DN references (e.g., when a user is deleted, ensure they are removed from all group memberships).
*   **Unique Attributes:** Guaranteeing that specific attributes (like `uid` or `mail`) have unique values across the directory.
*   **Entry USN (Update Sequence Number):** Essential for change tracking and replication.

=== 2.2. Hands-on Activity: Enabling and Configuring the Unique Attribute Plugin

In this activity, you will enable and configure the *Unique Attribute Plugin* to ensure that a specified attribute (e.g., `mail`) has a unique value across all entries in a specific suffix. This prevents duplicate email addresses or UIDs from being added to the directory, ensuring data integrity.

.Procedure

.  *Verify current status of the Unique Attribute Plugin (Optional)*
    You can list all configured plugins to see their current status.

    ```bash
    dsconf -D "cn=Directory Manager" ldap://localhost:389 plugin list
    ```
    Look for "Unique Attribute Plugin". By default, it's usually `off`.

.  *Attempt to add a duplicate entry (without the plugin enabled)*
    Let's try to add another user with the same email address as `jane.doe@example.com`.

    Create a file named `duplicate_mail.ldif`:

    ```ldif
    dn: uid=janet.smith,ou=People,dc=example,dc=com
    objectClass: top
    objectClass: person
    objectClass: organizationalPerson
    objectClass: inetOrgPerson
    uid: janet.smith
    cn: Janet Smith
    sn: Smith
    givenName: Janet
    mail: jane.doe@example.com
    userPassword: password
    ```

    Add this entry to the directory:

    ```bash
    ldapadd -x -D "cn=Directory Manager" -w password -f duplicate_mail.ldif -H ldap://localhost:389
    ```
    *Expected output:*
    ```
    adding new entry "uid=janet.smith,ou=People,dc=example,dc=com"
    ```
    Notice that the entry was successfully added because the plugin is not yet enabled, allowing duplicate `mail` values.

.  *Enable the Unique Attribute Plugin*
    Now, enable the plugin. You'll specify the `mail` attribute to be unique within the `ou=People,dc=example,dc=com` subtree.

    ```bash
    dsconf -D "cn=Directory Manager" ldap://localhost:389 plugin unique_attribute enable \
      --suffix "ou=People,dc=example,dc=com" --attribute mail
    ```
    *Expected output:*
    ```
    Successfully enabled plugin unique_attribute.
    ```
    [NOTE]
    ====
    For the Unique Attribute Plugin, the `dsconf` command creates a specific configuration entry under `cn=unique,cn=plugins,cn=config` that tells the plugin which attributes to enforce uniqueness on and within which subtrees.
    ====

.  *Restart the Directory Server instance*
    Many plugin configuration changes require a server restart to take full effect.

    ```bash
    dsctl instance1 restart
    ```
    *Expected output:*
    ```
    Restarting instance 'instance1'...
    Instance 'instance1' started.
    ```

.  *Attempt to add a duplicate entry again (with the plugin enabled)*
    Try adding the `janet.smith` entry with the duplicate `mail` address one more time.

    ```bash
    ldapadd -x -D "cn=Directory Manager" -w password -f duplicate_mail.ldif -H ldap://localhost:389
    ```
    *Expected output (will vary slightly but should indicate an error):*
    ```
    adding new entry "uid=janet.smith,ou=People,dc=example,dc=com"
    ldap_add: Constraint violation (19)
        additional info: A unique attribute plugin constraint was violated.
        Entry uid=janet.smith,ou=People,dc=example,dc=com (mail: jane.doe@example.com) clashes with uid=jane.doe,ou=People,dc=example,dc=com.
    ```
    Success! The server now prevents the addition of entries with duplicate `mail` attributes, thanks to the Unique Attribute Plugin.

.  *Disable the Unique Attribute Plugin (Cleanup)*
    To revert the change and allow duplicates (if desired for future testing, or simply for cleanup), you can disable the plugin.

    ```bash
    dsconf -D "cn=Directory Manager" ldap://localhost:389 plugin unique_attribute disable
    ```
    *Expected output:*
    ```
    Successfully disabled plugin unique_attribute.
    ```
    Remember to restart the server again after disabling:
    ```bash
    dsctl instance1 restart
    ```

=== 2.3. Expert Tip: Managing Plugins

*   **Check plugin documentation:** Each plugin has specific configuration parameters and behaviors. Always refer to the Red Hat Directory Server documentation for details.
*   **Ordered execution:** Some plugins have an order of execution that can be configured. This is important when plugins might interact or conflict.
*   **Monitor plugin logs:** Plugins often log their activities and errors to the main server error log. Always check logs if a plugin isn't behaving as expected.
*   **Performance impact:** While plugins add functionality, they also add processing overhead. Evaluate the impact of new plugins on server performance, especially during high load.
