#  Configure and enforce TLS 1.2/1.3 for secure client-server communication.

= Configure and Enforce TLS 1.2/1.3 for Secure Client-Server Communication

In modern enterprise environments, securing data in transit is paramount. Red Hat Directory Server (RHDS) often handles sensitive user and system identity information, making secure communication between clients and the server an absolute necessity. Transport Layer Security (TLS) is the cryptographic protocol that ensures this security by providing authentication, confidentiality, and data integrity.

== Understanding TLS for Red Hat Directory Server

TLS (Transport Layer Security) is the successor to SSL (Secure Sockets Layer) and is a cryptographic protocol designed to provide communication security over a computer network. When applied to RHDS, TLS protects the LDAP traffic exchanged between clients (e.g., applications, identity managers, user utilities) and the directory server.

=== Why is TLS Critical for RHDS?

Without TLS, LDAP communication occurs in plaintext, meaning anyone with network access could potentially intercept and read sensitive information such as usernames, passwords, search queries, and directory attributes. TLS addresses this by:

*   **Authentication:** Verifying the identity of the server to the client (and optionally the client to the server) using digital certificates. This prevents man-in-the-middle attacks.
*   **Confidentiality:** Encrypting all data transmitted between the client and server, making it unreadable to unauthorized parties.
*   **Integrity:** Ensuring that data has not been tampered with during transmission.

=== TLS 1.2 and TLS 1.3: The Secure Standards

Over time, vulnerabilities have been discovered in older versions of SSL and TLS protocols (e.g., SSLv2, SSLv3, TLSv1.0, TLSv1.1). Consequently, industry standards and compliance requirements mandate the use of stronger, more modern versions.

*   **TLS 1.2:** For many years, TLS 1.2 has been the industry standard for secure communication. It offers robust encryption algorithms and improved security over its predecessors.
*   **TLS 1.3:** The latest major version of the TLS protocol, TLS 1.3, provides enhanced security, performance, and privacy. It removes outdated and insecure features from previous versions and streamlines the handshake process, resulting in faster and more secure connections.

Red Hat Directory Server 13 supports both TLS 1.2 and TLS 1.3, allowing administrators to enforce the most secure protocols available. Disabling older, insecure protocols is a critical step in hardening your RHDS deployment.

== Configuring TLS 1.2/1.3 on Red Hat Directory Server

Configuring TLS for RHDS involves several key steps: obtaining or generating server certificates, configuring the server to use these certificates, and then explicitly enforcing the desired TLS protocol versions.

=== Prerequisites: Certificates and Key Database

Before RHDS can use TLS, it requires a server certificate stored in its Network Security Services (NSS) certificate database. This database is automatically initialized during the `dscreate` process when an instance is first created.

For a production environment, you would typically obtain a certificate signed by a trusted Certificate Authority (CA). For lab environments or initial testing, a self-signed certificate can be used.

[NOTE]
The management of server certificates using `certutil` and `dsconf` is covered in detail in a separate module. For this lab, we will generate a basic self-signed certificate to demonstrate TLS enforcement.

=== Step-by-Step Configuration

The following hands-on lab activity will guide you through configuring your RHDS instance to enforce TLS 1.2 and disable older, less secure protocols.

==== Lab Activity: Configure TLS 1.2/1.3 for RHDS

In this lab, you will generate a self-signed certificate, configure RHDS to use it, enforce TLS 1.2 as the minimum protocol version, and then test the secure connection.

===== 1. Access the RHDS Server

Ensure you are logged in to your RHEL 9 system where RHDS 13 is installed, as the `root` user or a user with `sudo` privileges.

===== 2. Identify Your RHDS Instance's NSS Database Path

The NSS certificate database is typically located within your RHDS instance's configuration directory.
Replace `instance_name` with the actual name of your RHDS instance.

```bash
# Example: If your instance is named 'my_rhds'
ls -d /etc/dirsrv/slapd-my_rhds/
```

The database files (e.g., `cert8.db`, `key3.db`, `secmod.db`) will be within this directory. The path to this directory is your NSS database path.

===== 3. Generate a Self-Signed Server Certificate

For this lab, we will create a basic self-signed certificate. In a production environment, you would follow your organization's PKI procedures.

[NOTE]
The `certutil` command is a powerful utility for managing NSS certificate databases. It's crucial to specify the correct database path and password.

.Create a new certificate in the RHDS NSS database:
```bash
# Replace 'my_rhds' with your instance name
# Replace 'YourOrg' with your organization name
# Replace 'rhds.example.com' with your server's FQDN
# The database password might be empty or a password you set during dscreate.
# If prompted for a password, press Enter if no password was set, or enter the correct password.

certutil -S \
  -n "Server-Cert" \
  -s "cn=rhds.example.com,ou=YourOrg,o=Example" \
  -t "CT,C,C" \
  -x \
  -2 \
  -m 120 \
  -v 10 \
  -d /etc/dirsrv/slapd-my_rhds \
  -f /etc/dirsrv/slapd-my_rhds/pin.txt \
  -w $(cat /etc/dirsrv/slapd-my_rhds/pin.txt)
```

[SUBSCRIPTIONS]
*   `-S`: Generate a new certificate.
*   `-n "Server-Cert"`: The nickname for the certificate in the database.
*   `-s "cn=rhds.example.com,ou=YourOrg,o=Example"`: The subject of the certificate. Ensure `cn` matches your server's FQDN.
*   `-t "CT,C,C"`: Trust attributes for the certificate (SSL Server, CA, Email Signer).
*   `-x`: Self-signed certificate.
*   `-2`: Version 2 or 3 certificate.
*   `-m 120`: Validity period in months (10 years).
*   `-v 10`: Certificate version.
*   `-d /etc/dirsrv/slapd-my_rhds`: Path to the NSS database.
*   `-f /etc/dirsrv/slapd-my_rhds/pin.txt`: File containing the database password. RHDS stores its database password in this file by default.
*   `-w $(cat /etc/dirsrv/slapd-my_rhds/pin.txt)`: Provides the password to `certutil` from the pin.txt file.

.Verify the certificate was added:
```bash
certutil -L -d /etc/dirsrv/slapd-my_rhds -f /etc/dirsrv/slapd-my_rhds/pin.txt
```
You should see `Server-Cert` listed.

===== 4. Configure RHDS to Use the Certificate and Enforce TLS Versions

Now, use `dsconf` to tell RHDS to use the generated certificate and set the minimum acceptable TLS version.

[IMPORTANT]
The `dsconf` utility is a powerful tool for modifying RHDS configuration. Always use it carefully.

.Set the server certificate nickname:
```bash
dsconf -D "cn=Directory Manager" ldap://localhost -b "cn=config" set-server-cert "Server-Cert"
```
You will be prompted for the `Directory Manager` password.

.Enforce a minimum TLS version of 1.2:
This command tells RHDS to reject connections using SSLv2, SSLv3, TLSv1.0, and TLSv1.1. It will only allow TLS 1.2 and newer (like TLS 1.3 if the client also supports it).

```bash
dsconf -D "cn=Directory Manager" ldap://localhost -b "cn=config" set-security-prop \
  min-ssl-version=TLS1.2 \
  security-protocol="TLS1.2,TLS1.3"
```
[SUBSCRIPTIONS]
*   `min-ssl-version=TLS1.2`: Sets the minimum allowed TLS protocol version to 1.2. Connections using older protocols will be rejected.
*   `security-protocol="TLS1.2,TLS1.3"`: Explicitly lists the protocols that RHDS should enable. This is often used in conjunction with `min-ssl-version` for fine-grained control. Omitting older, insecure protocols here effectively disables them.

===== 5. Restart Red Hat Directory Server

For these changes to take effect, the RHDS instance must be restarted.

```bash
dsctl restart my_rhds
```
Replace `my_rhds` with your instance name.

===== 6. Test Secure Client-Server Communication

You can test the secure connection using `ldapsearch`. We'll test both LDAPS (LDAP over SSL/TLS) and STARTTLS.

.Test LDAPS (port 636):
First, ensure that the LDAPS port (636) is enabled and listening. RHDS typically enables this by default with SSL configured.

```bash
ldapsearch -H ldaps://localhost -D "cn=Directory Manager" -w YourDMpassword -b "cn=config"
```
[NOTE]
For `ldaps://` to work, the client needs to trust the server's certificate. Since we used a self-signed certificate, the client might not inherently trust it. For this test, `ldapsearch` might still connect, but in a production setup, you would add the server's CA certificate to the client's trust store.

.Test STARTTLS (port 389):
STARTTLS allows an insecure LDAP connection on port 389 to be upgraded to a secure TLS connection.

```bash
ldapsearch -H ldap://localhost -x -ZZ -D "cn=Directory Manager" -w YourDMpassword -b "cn=config"
```
[SUBSCRIPTIONS]
*   `-H ldap://localhost`: Connects to the standard LDAP port (389).
*   `-x`: Simple authentication (bind).
*   `-ZZ`: Attempts to establish a STARTTLS session. If STARTTLS fails, the operation will terminate.
*   `-D "cn=Directory Manager"` and `-w YourDMpassword`: Directory Manager credentials.
*   `-b "cn=config"`: Base DN for the search.

If the commands execute successfully and return results, it indicates that the secure communication channels are working correctly with TLS enabled. If you encounter errors, it might be due to certificate issues, incorrect database passwords, or firewall rules blocking port 636.

== Best Practices and Troubleshooting Tips

*   **Use Trusted CAs:** In production, always use certificates signed by a trusted Certificate Authority (internal or public) to ensure client trust without manual intervention.
*   **Keep Protocols Updated:** Regularly review security advisories and update your RHDS configuration to disable any newly identified insecure protocols or ciphers.
*   **Monitor Logs:** Check the RHDS error logs (`/var/log/dirsrv/slapd-instance_name/errors`) for any TLS-related errors or warnings during connection attempts.
*   **Firewall Rules:** Ensure that the necessary ports (e.g., 389 for STARTTLS, 636 for LDAPS) are open in your firewall configuration on the RHDS server.
*   **Client Trust Stores:** For `ldaps://` and STARTTLS to work seamlessly, clients must trust the RHDS server's certificate. If using a custom or internal CA, distribute its root certificate to all client systems and configure their LDAP clients to trust it.
*   **Ciphers Suites:** While this section focuses on TLS versions, always review and restrict the cipher suites used to strong, modern algorithms. This is often configured in the same `dsconf set-security-prop` command.
