#  Configure persistent storage for containerized RHDS data.

= Configure Persistent Storage for Containerized Red Hat Directory Server 13

Directory services like Red Hat Directory Server (RHDS) manage critical identity and access information. When deploying RHDS in a containerized environment, ensuring data persistence is paramount. Without proper persistent storage, any data written by the Directory Server instance inside the container would be lost once the container is stopped, removed, or encounters a failure. This section delves into the importance of persistent storage for containerized RHDS and provides practical methods using Podman.

== Understanding Persistent Storage for Containers

Containers are designed to be ephemeral by nature. This means that any changes made to the container's filesystem during its lifecycle are typically lost when the container exits or is removed. For stateless applications, this behavior is acceptable and even desirable. However, for stateful applications like database servers, message queues, or directory servers, it's crucial to preserve application data independently of the container's lifecycle.

For Red Hat Directory Server, the critical data includes:

*   The actual LDAP database files (containing entries, attributes, etc.).
*   Server configuration files.
*   Log files.

Losing this data would result in a complete loss of your directory service, requiring a full rebuild and potentially data re-import, which is unacceptable in production environments.

Podman, a daemonless container engine, provides several mechanisms to achieve persistent storage for containers, primarily:

*   xref:configure-persistent-storage.adoc#_podman_volumes[Podman Volumes]
*   xref:configure-persistent-storage.adoc#_bind_mounts[Bind Mounts]

Each method has its advantages and use cases, offering flexibility depending on your operational requirements.

=== Podman Volumes

Podman volumes are the preferred method for persisting data generated by and used by Podman containers. Volumes are entirely managed by Podman, making them easier to back up, migrate, and use across different containers. When you create a volume, Podman provisions a dedicated storage area on the host system that is independent of the container's writable layer.

[NOTE]
Podman volumes are stored in a specific location on the host system, typically under `/var/lib/containers/storage/volumes/` (for rootful Podman) or `~/.local/share/containers/storage/volumes/` (for rootless Podman). You typically interact with them via `podman volume` commands rather than directly managing files within these paths.

*   *Benefits:*
    *   **Managed by Podman:** Podman handles the creation, management, and deletion of volumes.
    *   **Data Isolation:** Data is stored in a dedicated part of the host filesystem, separate from container layers.
    *   **Portability:** Volumes can be easily backed up, restored, and moved between hosts (though this often involves external tools).
    *   **No Host Path Conflicts:** You don't need to worry about host path permissions or ownership as much as with bind mounts, as Podman manages the volume's underlying storage.

==== How Podman Volumes Work

When you create a named volume, Podman sets up a directory on the host. When you run a container and attach this volume, the data written to the specified mount point inside the container is redirected to this host directory. This ensures that even if the container is removed, the data persists on the host within the volume.

[IMPORTANT]
If you mount an *empty* volume to a container directory that *already contains files*, the existing files in the container directory will be _obscured_ by the empty volume. If you mount a *non-empty* volume to a container directory, the contents of the volume will be present in the container, and any new data written to that directory in the container will go to the volume. For RHDS, it's common to mount volumes to the specific data directories.

=== Bind Mounts

Bind mounts allow you to mount an existing file or directory from the host system directly into a container. This gives you granular control over the exact location of your persistent data on the host.

*   *Benefits:*
    *   **Direct Host Control:** You specify the exact host path, which can be useful for sharing specific configuration files or logs.
    *   **Simplicity:** For quick tests or when you need direct access to the container's data from the host filesystem, bind mounts are straightforward.

*   *Considerations:*
    *   **Permissions (SELinux):** Bind mounts often require careful management of file permissions and SELinux contexts on the host to ensure the container can read and write data. Misconfigured permissions are a common source of errors.
    *   **Host Dependency:** The container is directly dependent on the host's filesystem structure.
    *   **Less Portable:** Moving data is less straightforward than with volumes, as it involves manually copying host directories.

==== How Bind Mounts Work

You specify a host path and a container path. Podman then "binds" the host path to the container path. Any changes made to the files within that path inside the container are directly reflected in the host path, and vice versa.

[source,bash]
----
# Syntax for bind mount
podman run -v /host/path:/container/path ...
----

=== RHDS Critical Data Paths

For containerized Red Hat Directory Server, the key directories that require persistent storage are:

*   `/var/lib/dirsrv/slapd-<instance_name>/db`: This directory contains the actual LDAP database files (e.g., `*.ldif`, `*.db4`, `*.id`). *This is the most critical directory to persist.*
*   `/etc/dirsrv/slapd-<instance_name>`: This directory contains instance-specific configuration files, including server settings, schema files, and certificate database files.
*   `/var/log/dirsrv/slapd-<instance_name>`: This directory contains server logs (access logs, error logs, audit logs). Persisting logs is crucial for troubleshooting and auditing.

[IMPORTANT]
When using the official Red Hat Directory Server container image, the `dscreate` command (used to initialize a new instance) will create these directories *inside* the container at the specified paths. If you mount an *empty* volume to these paths *before* running `dscreate`, the data will be written directly to the volume. If you mount a volume *after* `dscreate` has run and populated the container's internal paths, you'll need to manually move the data or ensure your `dscreate` command targets the mounted volume path. The common best practice is to mount the volumes *before* initialization.

== Hands-on Lab: Deploy RHDS with Persistent Storage using Podman Volumes

In this lab, you will deploy a Red Hat Directory Server 13 instance within a Podman container, ensuring its critical data (database, configuration, and logs) is persisted using named Podman volumes. You will verify persistence by adding a test entry, removing the container, and then launching a new container that reuses the same persistent volumes.

=== Prerequisites

*   A RHEL 9 system with Podman installed.
*   Access to the Red Hat Container Registry (registry.redhat.io) to pull the RHDS 13 image. Ensure you are logged in using `podman login registry.redhat.io`.
*   Basic understanding of Podman commands.

=== Lab Objectives

*   Create dedicated Podman volumes for RHDS database, configuration, and logs.
*   Run the RHDS 13 container, mounting the created volumes.
*   Initialize the RHDS instance inside the container.
*   Verify data persistence by adding an LDAP entry, removing the container, and then restarting a new container with the same volumes.

=== Steps

.Create Podman Volumes
++++
First, create the named volumes that will store your RHDS instance's data, configuration, and logs. We will name them reflectively for our `example` instance.

[source,bash]
----
podman volume create rhds-example-db
podman volume create rhds-example-config
podman volume create rhds-example-logs
----

You can list the created volumes to verify:

[source,bash]
----
podman volume ls
----

.Pull the RHDS 13 Container Image
++++
Ensure you have the latest RHDS 13 image available locally. You might need to log in to the Red Hat Container Registry first.

[source,bash]
----
# If not already logged in:
# podman login registry.redhat.io

podman pull registry.redhat.io/rhel9/dirsrv-13
----

.Run the RHDS Container with Mounted Volumes
++++
Now, run the RHDS container, mounting the volumes to the respective critical directories. We'll give our container a name for easy management, e.g., `rhds-example`.

[source,bash]
----
podman run -d \
  --name rhds-example \
  -p 389:389 -p 636:636 \
  -v rhds-example-db:/var/lib/dirsrv/slapd-example/db \
  -v rhds-example-config:/etc/dirsrv/slapd-example \
  -v rhds-example-logs:/var/log/dirsrv/slapd-example \
  registry.redhat.io/rhel9/dirsrv-13
----

*   `-d`: Runs the container in detached mode (in the background).
*   `--name rhds-example`: Assigns a name to the container.
*   `-p 389:389 -p 636:636`: Maps the standard LDAP (389) and LDAPS (636) ports from the container to the host.
*   `-v rhds-example-db:/var/lib/dirsrv/slapd-example/db`: Mounts the `rhds-example-db` volume to the LDAP database directory inside the container.
*   `-v rhds-example-config:/etc/dirsrv/slapd-example`: Mounts the `rhds-example-config` volume to the configuration directory.
*   `-v rhds-example-logs:/var/log/dirsrv/slapd-example`: Mounts the `rhds-example-logs` volume to the logs directory.

Check the container status:

[source,bash]
----
podman ps
----

.Initialize the RHDS Instance
++++
Access the running container and use `dscreate` to initialize a new RHDS instance named `example`. You'll need to provide an admin user (e.g., `admin`) and a password.

[source,bash]
----
podman exec -it rhds-example dscreate create \
  --instance-name example \
  --ldap-port 389 \
  --ldaps-port 636 \
  --suffix "dc=example,dc=com" \
  --root-dn "cn=Directory Manager" \
  --root-dn-password "SecretP@ssword1" \
  --system-user "dirsrv" \
  --system-group "dirsrv" \
  --silent
----

[IMPORTANT]
Replace `"SecretP@ssword1"` with a strong password of your choice.

The `dscreate` command will create and configure the RHDS instance, writing all its data and configuration files to the mounted volumes. The `--silent` option helps suppress interactive prompts.

After initialization, the RHDS instance inside the container should start. You can check its status:

[source,bash]
----
podman exec -it rhds-example dsctl example status
----

.Add a Test LDAP Entry
++++
Now, let's add a simple user entry to verify data persistence. Create an LDIF file on your host, then copy it into the container and use `ldapadd`.

Create a file named `test_entry.ldif` on your host machine with the following content:

[source,ldif]
----
dn: uid=testuser,ou=People,dc=example,dc=com
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
cn: Test User
sn: User
uid: testuser
userPassword: password
----

Now, copy this file into the container:

[source,bash]
----
podman cp test_entry.ldif rhds-example:/tmp/test_entry.ldif
----

Add the entry using `ldapadd` from inside the container:

[source,bash]
----
podman exec -it rhds-example ldapadd -x -D "cn=Directory Manager" -w "SecretP@ssword1" -f /tmp/test_entry.ldif
----

Verify the entry exists:

[source,bash]
----
podman exec -it rhds-example ldapsearch -x -D "cn=Directory Manager" -w "SecretP@ssword1" -b "dc=example,dc=com" "(uid=testuser)"
----

You should see the `testuser` entry in the output.

.Remove and Re-run the Container (Verifying Persistence)
++++
This is the crucial step to demonstrate persistence. You will stop and remove the current `rhds-example` container. All data written directly to the container's ephemeral filesystem would be lost, but our volume-mounted data should persist.

[source,bash]
----
podman stop rhds-example
podman rm rhds-example
----

Now, run a *new* container with the *same* named volumes. This simulates an upgrade, replacement, or recovery scenario.

[source,bash]
----
podman run -d \
  --name rhds-example-new \
  -p 389:389 -p 636:636 \
  -v rhds-example-db:/var/lib/dirsrv/slapd-example/db \
  -v rhds-example-config:/etc/dirsrv/slapd-example \
  -v rhds-example-logs:/var/log/dirsrv/slapd-example \
  registry.redhat.io/rhel9/dirsrv-13
----

Wait a moment for the new container to start and for the RHDS instance to fully initialize from the existing data in the volumes. You can monitor the logs if necessary:

[source,bash]
----
podman logs rhds-example-new
----

Once the server reports as started, verify the `testuser` entry again from the *new* container:

[source,bash]
----
podman exec -it rhds-example-new ldapsearch -x -D "cn=Directory Manager" -w "SecretP@ssword1" -b "dc=example,dc=com" "(uid=testuser)"
----

You should still see the `testuser` entry, demonstrating that your data persisted across container removal and recreation!

.Cleanup (Optional)
++++
To clean up all resources created in this lab:

[source,bash]
----
podman stop rhds-example-new
podman rm rhds-example-new
podman volume rm rhds-example-db rhds-example-config rhds-example-logs
----
++++

=== Expert Insights and Troubleshooting

*   **SELinux Contexts:** When using bind mounts, especially for rootful Podman on RHEL systems, SELinux can prevent containers from accessing host paths. You might see `Permission denied` errors in container logs. To resolve this, ensure the correct SELinux context is applied to the host directory, or temporarily disable SELinux (not recommended for production).
    [source,bash]
    ----
    # Example to change SELinux context for a host directory
    sudo chcon -Rt container_file_t /path/to/host/data
    ----
    Or, you can use the `:z` or `:Z` mount options with Podman (use `:z` for shared volumes, `:Z` for private unshared volumes):
    [source,bash]
    ----
    podman run ... -v /host/path:/container/path:z ...
    ----

*   **Permissions within Volumes:** Even with Podman volumes, ensure that the user ID (UID) and group ID (GID) within the container that owns the RHDS processes (typically `dirsrv`) has appropriate read/write permissions to the mounted volume paths. The RHDS container image usually handles this automatically by setting up the `dirsrv` user with the correct permissions within the container's entrypoint script when volumes are empty upon first use.

*   **Volume Data Corruption:** In rare cases of abrupt host shutdowns or filesystem issues, volume data can become corrupted. Implement robust backup and restore procedures for your Podman volumes, just as you would for any critical database.

*   **Inspecting Volume Contents:** While volumes are managed by Podman, you can still inspect their contents if needed by mounting them to a temporary utility container.
    [source,bash]
    ----
    podman run --rm -it -v rhds-example-db:/data alpine ls -l /data
    ----

*   **Choosing Between Volumes and Bind Mounts:**
    *   **Podman Volumes:** Generally recommended for core application data (like the LDAP database) due to better management, portability, and automatic handling of permissions (to some extent).
    *   **Bind Mounts:** Useful for specific scenarios like injecting custom configuration files from the host, reading host-based certificates, or when you explicitly need the data to be in a user-controlled host directory for other applications to access directly. Always be mindful of SELinux and filesystem permissions with bind mounts.

By correctly configuring persistent storage, you ensure that your containerized Red Hat Directory Server deployments are robust, reliable, and production-ready, preserving your critical identity data across container lifecycles.
