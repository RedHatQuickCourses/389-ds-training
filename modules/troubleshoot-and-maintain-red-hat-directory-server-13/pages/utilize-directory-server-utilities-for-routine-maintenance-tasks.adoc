#  Utilize directory server utilities for routine maintenance tasks.

= Utilize Directory Server Utilities for Routine Maintenance Tasks
:navtitle: RHDS Maintenance Utilities
:page-aliases: rhds-maintenance-utilities.adoc

Routine maintenance is a cornerstone of ensuring the long-term health, stability, and performance of any production system, and Red Hat Directory Server (RHDS) is no exception. Proactive maintenance helps in identifying and resolving potential issues before they escalate, maintaining data integrity, optimizing performance, and ensuring the availability of directory services. This section delves into the essential utilities provided by RHDS 13 that administrators can leverage for these critical routine maintenance tasks.

== Understanding Routine Directory Server Maintenance

Red Hat Directory Server provides a centralized repository for identity and access management, making its continuous operation vital for many enterprise services. Regular maintenance ensures:

*   **Data Integrity:** Prevents corruption and inconsistencies within the directory database.
*   **Optimal Performance:** Keeps the server running efficiently by addressing potential bottlenecks and ensuring indexes are sound.
*   **Security Posture:** Helps in reviewing and maintaining security configurations.
*   **Availability:** Reduces the risk of unexpected downtime due to preventable issues.
*   **Compliance:** Facilitates regular auditing and reporting of directory state.

The utilities covered here are designed to assist administrators in these areas, offering tools for monitoring, configuration verification, data consistency checks, and controlled data manipulation.

=== Key Maintenance Utilities

RHDS provides a suite of command-line utilities that are indispensable for day-to-day administration and maintenance. While many tools serve multiple purposes, we'll focus on their application in routine maintenance.

*   xref:./install-configure-rhds.adoc#_dsctl_managing_rhds_instance_lifecycle_start_stop_restart_with_dsctl[`dsctl`]: The primary tool for managing the lifecycle of an RHDS instance (start, stop, restart, status). Essential for ensuring the server is operational or for controlled shutdowns during maintenance windows.
*   xref:./install-configure-rhds.adoc#_dsconf_basic_server_configuration_using_dsconf_and_dsidm[`dsconf`]: Used for viewing and modifying server configuration parameters. Critical for auditing current settings and applying minor adjustments.
*   xref:./manage-directory-data.adoc#_execute_efficient_ldap_searches_to_retrieve_directory_information[`ldapsearch`]: A powerful client utility for querying directory data. In maintenance, it's used to verify data integrity, check for expected entries, and troubleshoot data-related issues.
*   `fixup-slapd`: A crucial utility for diagnosing and repairing inconsistencies within the RHDS database files.
*   `db2ldif`: Exports directory data from the database to an LDIF (Lightweight Directory Interchange Format) file. Useful for creating consistent snapshots for auditing, comparison, or partial backups.
*   `dsloganalzyer`: (Though often used for troubleshooting performance) Can be used in routine checks to identify unusual patterns or errors in logs.

Let's explore some of these in more detail concerning routine maintenance.

==== dsctl: Instance Control Utility for Status Checks

The `dsctl` utility is your first point of contact for checking the operational status of your RHDS instance. Regularly verifying that the server is running as expected is a fundamental maintenance task.

.Technical Explanation
`dsctl` communicates with the `systemd` service manager to control and query the status of RHDS instances. Each RHDS instance typically has its own `systemd` service unit, making `dsctl` an effective wrapper for managing these units. For routine maintenance, the `status` subcommand is invaluable for a quick health check.

.Syntax
[subs=+attributes]
```bash
dsctl <instance_name> status
```
Where `<instance_name>` is the name given to your RHDS instance during creation (e.g., `dirsrv`).

.Example
To check the status of an RHDS instance named `dirsrv`:
[subs=+attributes]
```bash
dsctl dirsrv status
```
.Expected Output
[subs=+attributes]
```text
● dirsrv.service - 389 Directory Server dirsrv
   Loaded: loaded (/usr/lib/systemd/system/dirsrv@.service; enabled; vendor preset: disabled)
   Active: active (running) since Tue 2023-10-26 10:00:00 UTC; 1 day ago
     Docs: man:dirsrv(8)
 Main PID: 1234 (ns-slapd)
    Tasks: 21 (limit: 23616)
   Memory: 78.5M
   CGroup: /system.slice/system-dirsrv.slice/dirsrv@dirsrv.service
           └─1234 /usr/sbin/ns-slapd -D /etc/dirsrv/slapd-dirsrv -i /run/dirsrv/slapd-dirsrv.pid
```
This output confirms the instance `dirsrv` is `active (running)`.

==== dsconf: Configuration Verification

`dsconf` allows administrators to inspect various configuration settings of the RHDS instance. During routine maintenance, it's good practice to periodically review critical configurations to ensure they haven't been inadvertently changed or drifted from desired settings.

.Technical Explanation
`dsconf` interacts with the configuration entries stored within the directory server itself, specifically under the `cn=config` suffix. It provides a user-friendly interface to query and modify these entries, abstracting the underlying LDAP operations. For maintenance, you might want to check plugin statuses, database settings, or security configurations.

.Syntax
[subs=+attributes]
```bash
dsconf <instance_name> config get <attribute_name>
dsconf <instance_name> config list
```
.Example: Check Listener Port
To verify the standard LDAP listener port:
[subs=+attributes]
```bash
dsconf dirsrv config get nsslapd-port
```
.Example: List All Config Attributes
To get a broader overview of the configuration:
[subs=+attributes]
```bash
dsconf dirsrv config list
```

==== ldapsearch: Directory Data Query for Integrity Checks

`ldapsearch` is not just for client applications; it's a powerful tool for administrators to perform ad-hoc queries and verify the presence, absence, and correctness of directory data. This is fundamental for routine data integrity checks.

.Technical Explanation
`ldapsearch` is a command-line client that connects to an LDAP server and executes search operations based on specified criteria. For maintenance, you can use it to:
*   Verify that critical entries (e.g., administrator accounts, core groups) exist and have the correct attributes.
*   Check the number of entries in a specific subtree.
*   Look for duplicate entries (if not prevented by schema rules).
*   Ensure that indexed attributes return results quickly.

.Syntax
[subs=+attributes]
```bash
ldapsearch -h <hostname> -p <port> -D "cn=Directory Manager" -w <password> -b <base_dn> <search_filter> <attributes_to_return>
```
.Example: Verify Administrator Entry
To ensure the `Directory Manager` entry is present:
[subs=+attributes]
```bash
ldapsearch -h localhost -p 389 -D "cn=Directory Manager" -w "Password123" -b "cn=config" "cn=Directory Manager"
```
.Example: Count Users in a Specific OU
To count the number of users in an organizational unit `ou=people,dc=example,dc=com`:
[subs=+attributes]
```bash
ldapsearch -h localhost -p 389 -D "cn=Directory Manager" -w "Password123" -b "ou=people,dc=example,dc=com" "(objectclass=inetorgperson)" dn | grep "dn:" | wc -l
```

==== fixup-slapd: Database Integrity Utility

`fixup-slapd` is a critical utility for advanced maintenance, specifically for diagnosing and repairing potential corruption or inconsistencies within the RHDS database files (often caused by abnormal shutdowns or underlying file system issues).

.Technical Explanation
RHDS uses Berkeley DB or LMDB (depending on configuration) to store directory data. Over time, or due to unforeseen events, these databases can develop inconsistencies. `fixup-slapd` operates directly on these database files (while the server is *stopped*), checking for and attempting to fix errors like corrupted entries, invalid internal pointers, or index mismatches. It's crucial to understand that running `fixup-slapd` should always be preceded by a full backup, as it modifies the database directly.

.When to Use `fixup-slapd`
*   After an abnormal server shutdown.
*   If you observe persistent errors in the server logs related to database operations.
*   If `ldapsearch` operations return unexpected errors or incomplete data.
*   As part of a scheduled, comprehensive maintenance window.

.Syntax
[subs=+attributes]
```bash
# First, stop the RHDS instance
dsctl <instance_name> stop

# Then run fixup-slapd
fixup-slapd -D /etc/dirsrv/slapd-<instance_name>
```
.Important Considerations
*   **Always back up your directory data *before* running `fixup-slapd`**. This utility performs irreversible changes.
*   The RHDS instance *must be stopped* before running `fixup-slapd`. Running it on a live server can lead to further data corruption.
*   Review the output of `fixup-slapd` carefully. It will report any issues found and whether they were fixed.

==== db2ldif: Database Export Utility for Verification

The `db2ldif` utility exports the entire directory database or specific subtrees into an LDIF file. While often associated with backup procedures, it's also useful for routine maintenance for verification and auditing purposes.

.Technical Explanation
`db2ldif` reads the internal database files of an RHDS instance (while it's *stopped* or *online* with certain options) and writes the content to an LDIF file. This LDIF file represents a text-based snapshot of your directory data. For routine maintenance, you can export the data periodically and compare it with previous exports to detect unexpected changes, or use the LDIF file for offline analysis and auditing.

.Syntax
[subs=+attributes]
```bash
# To export while the server is running (recommended for maintenance checks as it avoids downtime)
db2ldif -a <archive_directory> -D /etc/dirsrv/slapd-<instance_name>

# To export while the server is stopped (less common for routine verification, more for full backups)
# db2ldif -a <archive_directory> -D /etc/dirsrv/slapd-<instance_name> -Z
```
*   `-a <archive_directory>`: Specifies the directory where the LDIF and other files will be created.
*   `-D /etc/dirsrv/slapd-<instance_name>`: Specifies the configuration directory of the RHDS instance.
*   `-Z`: If specified, the utility expects the server to be *stopped*. Without `-Z`, it performs an online export using `cn=Export,cn=plugins,cn=config`.

.Example: Online Export for Verification
[subs=+attributes]
```bash
mkdir -p /var/lib/dirsrv/slapd-dirsrv/ldif_exports/$(date +%Y%m%d)
db2ldif -a /var/lib/dirsrv/slapd-dirsrv/ldif_exports/$(date +%Y%m%d) -D /etc/dirsrv/slapd-dirsrv
```
This command exports the directory data to a timestamped directory, allowing for easy comparison with previous exports.

== Hands-on Lab: Performing Routine RHDS Maintenance
[discrete]
.Lab: Performing Routine RHDS Maintenance
This lab guides you through using essential Red Hat Directory Server utilities for routine maintenance tasks, including checking server status, verifying configuration, inspecting directory data, and understanding how to prepare for database integrity checks.

=== Prerequisites
*   An installed and running Red Hat Directory Server 13 instance (e.g., named `dirsrv`) on RHEL 9.
*   Access to the server's command line with `sudo` privileges.
*   The `Directory Manager` password (e.g., `Password123`).
*   Some existing user or group data in your directory for search operations (you might have created this in previous labs, e.g., `dc=example,dc=com`). If not, you can create a test entry using `ldapadd` before starting the lab.

==== Create a Test Entry (Optional, if no data exists)

If your directory is empty, let's quickly add a test user for later search operations.

.Create `testuser.ldif` file:
[source,bash]
----
cat << EOF > /tmp/testuser.ldif
dn: uid=testuser,ou=people,dc=example,dc=com
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
uid: testuser
cn: Test User
sn: User
givenName: Test
mail: testuser@example.com
userPassword: testpassword
EOF
----

.Add the entry to the directory:
[source,bash,subs=+attributes]
----
ldapadd -x -h localhost -p 389 -D "cn=Directory Manager" -w "Password123" -f /tmp/testuser.ldif
----
.Expected Output
```text
adding new entry "uid=testuser,ou=people,dc=example,dc=com"
```

=== Steps

. Step 1: Verify RHDS Instance Status
Regularly checking the server status is the first step in any maintenance routine.

.. Check the status of your `dirsrv` instance:
+
[source,bash,subs=+attributes]
----
sudo dsctl dirsrv status
----

.. Observe the output to confirm that the service is `active (running)`.

. Step 2: Inspect Key Server Configuration
Periodically review critical server configurations to ensure settings are as expected.

.. Check the LDAP listener port for your instance:
+
[source,bash,subs=+attributes]
----
sudo dsconf dirsrv config get nsslapd-port
----

.. Check the number of threads for database operations:
+
[source,bash,subs=+attributes]
----
sudo dsconf dirsrv config get nsslapd-threadnumber
----

.. List all configured plugins to verify expected functionality:
+
[source,bash,subs=+attributes]
----
sudo dsconf dirsrv plugin list
----

. Step 3: Perform Basic Data Integrity Checks with `ldapsearch`
Use `ldapsearch` to confirm the presence and accessibility of directory data.

.. Search for the `Directory Manager` entry to verify core configuration data:
+
[source,bash,subs=+attributes]
----
ldapsearch -x -h localhost -p 389 -D "cn=Directory Manager" -w "Password123" -b "cn=config" "cn=Directory Manager" cn
----

.. Search for the test user you created (or any existing user) in the `ou=people` subtree:
+
[source,bash,subs=+attributes]
----
ldapsearch -x -h localhost -p 389 -D "cn=Directory Manager" -w "Password123" -b "ou=people,dc=example,dc=com" "(uid=testuser)" cn sn mail
----

.. Count the total number of entries under your base DN (e.g., `dc=example,dc=com`) to monitor growth or identify unexpected changes:
+
[source,bash,subs=+attributes]
----
ldapsearch -x -h localhost -p 389 -D "cn=Directory Manager" -w "Password123" -b "dc=example,dc=com" "(objectclass=*)" dn | grep "dn:" | wc -l
----
+
This command counts all entries by looking for lines starting with "dn:".

. Step 4: Prepare for Database Integrity Fixes (Understanding `fixup-slapd`)
While we won't run `fixup-slapd` in this live lab due to the complexity of simulating database corruption, it's vital to understand its usage.

.. Before considering `fixup-slapd`, you would *always* perform a full backup of your instance.
+
[source,bash,subs=+attributes]
----
# Example: Full backup command
# sudo dsctl dirsrv backup /var/lib/dirsrv/backups/full_backup_$(date +%Y%m%d%H%M)
----
+
The backup ensures that you have a recovery point if `fixup-slapd` causes unintended issues.

.. `fixup-slapd` operates on a *stopped* server. If you were to run it, the steps would be:
+
[source,bash,subs=+attributes]
----
# 1. Stop the RHDS instance
# sudo dsctl dirsrv stop

# 2. Run fixup-slapd. The -D option points to the instance's configuration directory.
# sudo fixup-slapd -D /etc/dirsrv/slapd-dirsrv

# 3. Review the output for any errors or repairs made.

# 4. Start the RHDS instance after successful completion.
# sudo dsctl dirsrv start
----
+
*Reflect:* Why is it so crucial to stop the server before running `fixup-slapd`? (Answer: To prevent data inconsistency or further corruption while the utility is modifying the database files directly, bypassing the server's internal mechanisms).

. Step 5: Export Directory Data for Verification
Exporting data to LDIF format provides a snapshot that can be used for auditing or comparing against previous exports.

.. Create a dedicated directory for today's export:
+
[source,bash,subs=+attributes]
----
EXPORT_DIR="/var/lib/dirsrv/slapd-dirsrv/ldif_exports/$(date +%Y%m%d)"
sudo mkdir -p "$EXPORT_DIR"
echo "Exporting data to: $EXPORT_DIR"
----

.. Perform an online `db2ldif` export of your `dirsrv` instance:
+
[source,bash,subs=+attributes]
----
sudo db2ldif -a "$EXPORT_DIR" -D /etc/dirsrv/slapd-dirsrv
----

.. Verify the contents of the export directory. You should see `.ldif` files, including `schema.ldif` and files for your suffixes (e.g., `example.com.ldif`).
+
[source,bash,subs=+attributes]
----
sudo ls -l "$EXPORT_DIR"
----

.. You can now inspect the `example.com.ldif` file (or similar) to review the data in a human-readable format:
+
[source,bash,subs=+attributes]
----
sudo cat "$EXPORT_DIR"/example.com.ldif | head -n 20
----
+
This allows for visual inspection or programmatic comparison with previous exports to detect unauthorized changes or data anomalies.

== Expert Insights and Best Practices

*   **Schedule Regular Maintenance:** Integrate these tasks into a routine maintenance schedule. The frequency will depend on your environment's criticality, change rate, and auditing requirements.
*   **Automate Where Possible:** Many of these checks (e.g., `dsctl status`, `ldapsearch` for counts) can be scripted and integrated into monitoring systems.
*   **Monitor Logs:** `dsloganalzyer` and direct inspection of `/var/log/dirsrv/slapd-<instance_name>/errors` are crucial. Anomalies in logs often precede more significant issues.
*   **Test Backup and Restore:** While `db2ldif` provides an export, always regularly test your full backup and restore procedures to ensure they are viable in a disaster recovery scenario.
*   **Understand `fixup-slapd`'s Power:** Treat `fixup-slapd` with respect. It's a powerful tool but should only be used after exhausting other troubleshooting steps and *always* with a prior full backup. Misuse can worsen issues.
*   **Version Control Configuration:** Consider storing important `dsconf` outputs or configuration files under version control (e.g., Git) to track changes and revert if necessary.
*   **Document Your Environment:** Keep detailed records of your RHDS configuration, including base DNs, user/group structures, and any custom schema or plugins. This greatly aids troubleshooting and maintenance.
